Agent Memory · Cognee / Supermemory

Cognee / Supermemory: When Multiple Agents Share One Memory Service

The previous chapters separated the memory problem across layers: Mem0 as an external memory layer, Letta as stateful agents, Graphiti as a temporal graph, LangMem / LangGraph as workflow-time memory, and TencentDB-Agent-Memory as recoverable context offload for heavy tool logs, then OpenViking as one viking:// tree for resources, memories, skills, and sessions. Cognee and Supermemory turn memory into a shared service: when several agents, users, and data sources depend on it, which system ingests, processes, isolates, retrieves, and deletes the data?

Project: topoteretes/cognee Project: supermemoryai/supermemory Theme: knowledge layer and context API

Inside one agent, memory can sound like a narrow task: save what the user said and search it next time. A deployed product makes the job much larger. Content arrives from chats, files, web pages, drives, code repositories, and SaaS connectors. Processing may be queued. Results need user, project, or tenant scoping. Deletion has to be operational. Cognee and Supermemory are useful because they make those platform duties visible. 

Scenario: a team knowledge assistant needs long-term memory

Inputs are no longer only chat:
  meeting notes, design docs, web pages, Google Drive, GitHub issues, support history

Callers are no longer only one agent:
  chat agent, search page, ticket assistant, coding assistant, background sync worker

The platform must answer:
  Who owns this content?
  Which processing stage is it in?
  Should retrieval return a profile, evidence snippets, or graph relations?
  When the user withdraws data, what exactly must be deleted?

That is why Cognee and Supermemory should not be read as merely bigger RAG systems. They provide a shared memory service: how data enters, how it is processed, how each query stays within the right user or project, and how several callers can reuse the same knowledge safely.

Questions this article answers. After this chapter, you should be able to explain why Cognee's simple remember() call still expands into add(), cognify(), and optional improve(); why Supermemory's add, profile, search, and connectors read more like a product context API; and when a system needs a knowledge layer versus a packaged context platform.

A single document makes the contrast easier: a “customer escalation policy.” In Cognee, the question is how that document becomes reusable knowledge. In Supermemory, the question is how a product gets profile, search, and connector context through an API. The lifecycle table below lines up the two routes before the chapter studies them separately.

Stage Cognee route Supermemory route
Write entry add / remember accepts files, text, or URLs. add ingests source content, URLs, and metadata within a namespace.
Processing state cognify turns a dataset into a graph / vector retrieval layer. The API exposes queued, extracting, indexing, and done states while the hosted pipeline extracts and indexes.
Retrieval output search reads like a query against the processed knowledge layer. profile returns a stable profile; search returns query evidence.
Deletion scope Deleting a dataset must account for source material and derived graphs or vector indexes. Removing a product object or connector must clear data under the relevant namespace.

Source scope. This chapter uses the public topoteretes/cognee and supermemoryai/supermemory repositories, READMEs, docs, and visible source, pinned respectively to c0d18c8 and 2415a5c. Cognee's local SDK path can be traced directly. For Supermemory's hosted service, the discussion stays with public docs, SDK examples, and API schemas rather than inferring private extraction internals.

1. Why the last chapter covers a shared memory service

1.1 The earlier layers reappear when many callers share memory

Cognee and Supermemory are easier to read after the lower layers are clear. Otherwise both can be mistaken for larger RAG products. In this series order, they answer the next question: after write policies, state ownership, temporal graphs, execution paths, and context offload are known, what happens when memory becomes a shared service?

At platform scale, memory is no longer a capability of one agent. A product may ingest chats, documents, webpages, email, code repositories, and third-party apps. The same object may belong to a user, team, project, dataset, or tenant. A query may need a user profile, similar snippets, related files, graph relations, and permission-filtered evidence. Cognee and Supermemory therefore ask how long-term memory becomes infrastructure that several users, data sources, and callers can rely on.

1.2 User isolation, processing status, and deletion all matter

A memory platform has at least four public duties. Scope: user, project, dataset, and tenant boundaries. Process: extraction, chunking, embedding, graphing, indexing, or profile generation. Retrieve: returning graph context, user profiles, related documents, or model-ready context instead of only text chunks. Delete: giving callers a boundary they can remove when content, projects, or users are withdrawn.

Those duties map directly to common failures. If scope is unclear, one user's material can leak into another user's context. If process state is unclear, callers cannot tell whether content is queued, extracted, chunked, embedded, or indexed. If retrieval contracts are unclear, profile facts, evidence, and document snippets blur into one list. If deletion boundaries are unclear, disconnected connectors can keep influencing the model. The platform value is moving those responsibilities out of ad hoc application prompts.

2. Cognee: turn data into a reusable knowledge layer

Cognee presents itself as an open-source AI memory platform: ingest data in any format, build a self-hosted knowledge graph, and let agents recall and act with context. Its README also emphasizes domain entities, relationships, and custom ontologies. That positions Cognee as more than a vector index wrapper; it is trying to turn raw material into a connected intermediate layer. See the README overview.

2.1 The user API is simple; the processing pipeline is not

The user-facing API offers four common verbs: remember, recall, forget, and improve. remember() can store permanently in the knowledge graph, or store in a fast session memory when a session_id is supplied. recall() then routes a natural language query. The public shape is intentionally light; the pipeline under it is where the work happens.

The source makes that layering explicit. The remember() docstring splits ordinary text and document inputs into permanent memory and session memory. Permanent memory runs add() plus cognify(); session memory stores in a session cache and, by default, bridges into the permanent graph through self-improvement. The permanent path's internal _run() calls add(...), then cognify(...), then optionally improve(...). 

async def remember(data, dataset_name="main_dataset", session_id=None, self_improvement=True):
    if session_id:
        # session memory: fast cache, then optional bridge into permanent graph
        ...

    async def _run():
        await add(data=data, dataset_name=dataset_name, ...)
        cognify_result = await cognify(datasets=[dataset_name], ...)

        if self_improvement:
            await improve(dataset=dataset_name, user=user)

Session experience also needs an explicit destination. Current typed memory dispatch routes structured Q&A, traces, and feedback to their session records and returns entry_id and entry_type. A session binds to a dataset on its first write or activity-recording recall, and later entries follow that binding. _resolve_entry_dataset() rejects an explicit ID for another dataset and checks write access before caching content. After an initial concurrent binding, the code rereads the record to prevent competing writers from assigning the session to different knowledge sets.

For example, a support session already bound to an after-sales dataset rejects feedback targeting a sales dataset ID before writing it. Callers should retain returned dataset and entry IDs and observe session writes separately from long-term graph processing. Ordinary material continues through add → cognify; structured session entries use their type and binding to determine subsequent processing.

User action Platform responsibility Why it matters
remember(data) add ingests raw data, cognify builds the graph, and improve enriches it. The caller asks Cognee to remember; Cognee owns the multi-stage processing path.
remember(data, session_id) Session cache first, then optional bridge into the permanent graph. The current session stays fast while long-term knowledge can catch up.
recall(query) Route across session, graph, and graph-context sources depending on scope and query type. The same query may need fresh session context or durable graph knowledge.

The point at which “remember” returns depends on the calling mode. Default permanent writes await add, cognify, and enabled improve work. With run_in_background=True, the first await returns a running RememberResult. A second await result waits for the task. Background processing errors are stored in status/error rather than re-raised as they are on the default blocking path. done therefore means finished, not successful; inspect status too. This example disables improve to isolate graph construction: 

result = await cognee.remember(
    "Customer escalation policy...",
    dataset_name="company_docs",
    run_in_background=True,
    self_improvement=False,
)
await result
if result.status != "completed":
    raise RuntimeError(result.error or f"Pipeline status: {result.status}")

The background path retains an in-process asyncio task so garbage collection does not abandon it; that is not a durable queue that survives a process restart. The session path differs again: session_stored only says the session-write step returned, while background improve failures are logged. It cannot establish that the permanent graph has synchronized. Verify session readability, graph completion, and subsequent improvement separately.

2.2 add and cognify turn source material into a knowledge graph

add() accepts strings, files, URLs, binary streams, and datasets. Its documented workflow resolves data, extracts content, stores it in a dataset, tracks metadata, and assigns permissions. Cognee therefore begins before retrieval: it first makes ingestion a platform concern.

cognify() is the transformation step. Its docstring describes document classification, text chunking, entity extraction, relationship detection, graph construction, and content summarization. The point is not that a graph is always better than vectors. The point is that raw content becomes a reusable knowledge layer that several agents and search strategies can share.

Retrieval then exposes that layer. search() takes query type, datasets, node filters, neighborhood controls, references, and ranking parameters. Its documentation names GRAPH_COMPLETION, RAG_COMPLETION, CHUNKS, CYPHER, and lexical chunk search. The caller is not only asking for similar text; it is choosing how to interrogate the knowledge layer. 

await add(data, dataset_name="company_docs")

await cognify(
    datasets=["company_docs"],
    graph_model=KnowledgeGraph,
    chunker=TextChunker,
)

results = await search(
    query_text="How should we handle customer escalation?",
    query_type=SearchType.GRAPH_COMPLETION,
    datasets=["company_docs"],
    include_references=True,
)
Shape-level example: one document moving through Cognee

add / remember:
  source = "Customer escalation policy..."
  dataset = "company_docs"

cognify:
  the dataset is chunked, entities and relationships are extracted,
  and graph / vector retrieval layers are built

search:
  query = "Who should receive a customer escalation?"
  results come from the processed knowledge layer and can include references

Read through this chain and Cognee stops looking like "upload a file and vector-search it." add places material into a dataset; cognify performs classification, chunking, entity and relation extraction, and graph construction; search lets the caller choose graph answer, RAG answer, chunk search, Cypher, or lexical retrieval.

Current remember also accepts explicit content_type="code" or "skills" to select code-graph or Skill ingestion. It does not infer these intentions from a path alone. The add → cognify skeleton above describes ordinary material, not a single mandatory pipeline for every input type.

2.3 Cognee fits domain knowledge that many Agents must reuse

Cognee fits cases where an organization has documents, code, customer history, or expert patterns that should not be pasted into prompts turn by turn. The material should first be processed, connected, scoped, and made reusable. That is why its README examples lean toward company brain, customer support, and expert knowledge distillation scenarios.

The cost follows from the same design. A heavier knowledge layer brings processing latency, dataset permissions, graph schema choices, ontology questions, search modes, and deployment responsibilities. For a small user preference, this may be too much. For shared domain knowledge that many agents need to revisit, the Cognee route is natural.

2.4 Cognee is a knowledge-processing layer, not lightweight preference storage

A useful test is whether the material deserves to become an intermediate knowledge layer. The answer is usually yes when the material will be reused by several agents or workflows, when relationships and provenance matter more than a single text span, and when self-hosting or governance of the processing chain matters. If those signals are weak, datasets, cognify, graph search, and ontology choices may be unnecessary weight.

When those signals are strong, Cognee's benefit is not merely another search mode. It moves source material out of temporary prompts and into a reusable knowledge layer that can be improved, searched again, scoped by dataset, and shared by different agents working over the same organizational knowledge.

For documents worth graph construction whose processing cost is still unknown, remember(..., dry_run=True) offers a preliminary estimate. Its current scope is ordinary permanent ingestion in local mode: it does not ingest or call an LLM, and reports stage-level token and rough cost estimates. Extra model calls made by improve are excluded. Use it to compare input size and chunking choices, then measure quality and cost on the real pipeline.

3. Supermemory: package memory as a context API

Supermemory's README describes a memory and context layer for AI, with memory, user profiles, hybrid search, connectors, and multi-modal extractors in one stack. It also pitches a single API for AI products. That shifts the center of gravity from designing your own graph pipeline to calling packaged context APIs. See the README opening and developer quickstart.

3.1 Ingest within a namespace and choose whether to form memories

A customer-escalation policy is shared reference material; a reply preference belongs to personal memory. The v5 ingestion contract moves user or project scope into /ns/{namespace}, with namespace as the SDK’s first argument. Legacy containerTag leaves the body and customId becomes id. Applications select the namespace from the authenticated caller’s allowed scope.

taskType continues to choose the purpose: memory extracts durable memories, while superrag indexes source context. Default dreaming="dynamic" groups related documents; instant processes them individually. A new namespace can remain without memories or a profile for several minutes under dynamic processing. Applications should observe document processing and memory formation separately when designing the first-use experience.

await client.add("support-team", {
  content: "Customer escalation policy...",
  id: "support-escalation-policy",
  taskType: "superrag",
});

Adding the same id again appends or diffs incoming content. The document update contract uses documents.update(namespace, id, { content }) to replace the canonical source; facts supported only by the old source can disappear after reprocessing. group selects existing memories used during ingestion and takes effect on re-ingestion. New-document metadata, retrieval filters, and authorization have separate responsibilities.

Two observations for the same material:
POST /ns/support-team/document
  → returns id and the document's current processing state
GET /ns/support-team/document/{id}
  → observe extracting / chunking / embedding / indexing / done / failed

memory + dynamic:
  observe document processing and later memory / profile formation separately
superrag:
  produces source retrieval artifacts without personal memories

The initial response reports acceptance and the document’s state at that time. An unchanged duplicate can already return done; a metadata-only update to a failed document can still return failed. Callers should branch on that state rather than display every successful HTTP response as memory-ready.

3.2 Request profiles and search separately, then assemble their context

The v5 profile contract defines profile as maintained user background and removes q and threshold from the call. Static and dynamic sections are always returned. Buckets organize additional topics and include built-in preferences by default. Requesting selected buckets narrows only that section; it cannot disable static or dynamic.

Profile entries are now { id, memory } objects. Read the memory text and retain its ID. For a programming-style question, an application can request profile and search concurrently, then budget recurring background and turn-specific evidence separately:

const [background, evidence] = await Promise.all([
  client.profile("user_123", { buckets: ["preferences"] }),
  client.search("user_123", {
    query: "programming style",
    searchMode: "memories",
    threshold: 0.6,
  }),
]);
const stableFacts = background.profile.static.map((entry) => entry.memory);
const relevantResults = evidence.results;

Namespace bucket writes merge by name and preserve omitted buckets. Organization-owned buckets can appear in effective reads, but attempts to mutate them through namespace endpoints return 409. Profile-topic management therefore needs its own authority alongside memory-read scope.

3.3 Choose retrieval granularity and forgetting targets explicitly

The v5 search contract defaults to hybrid with a 0.3 threshold. Memories returns formed memories, chunks returns source chunks, and hybrid combines both. When migrating a v4 call, preserve memories and 0.6 explicitly for an initial comparison before broadening recall. Query, filter, include, and rerank belong in one request body; search accepts no query-string parameters.

Results distinguish memory and chunk fields, with source documents and related memories expanded through include options. Applications should inspect the returned fields before constructing citations. Two requests with the same namespace can still retrieve different material because their modes and thresholds differ.

“Forget the old address” also needs a fixed target set. The forgetting API supports semantic preview and exact-ID forgetting: review dryRun matches, then submit those IDs to the exact endpoint. Repeating semantic selection can choose a different set after data changes. Exact requests can partially succeed, so inspect matches and errors individually. v5 also removes legacy direct memory creation and update routes; changed facts enter processing through canonical document updates.

Connectors push the platform edge further outward. The docs list Google Drive, Gmail, Notion, OneDrive, GitHub, Granola, and Web Crawler as external sources that can sync into Supermemory. The connector workflow includes connection creation, user authorization, automatic setup, and continuous sync through webhooks or schedules. Once memory owns connectors, it also inherits OAuth, webhooks, file versions, sync status, and user-space boundaries.

Having a connector does not imply one uniform freshness guarantee. In the current capability table, Granola is manual on-demand only, Web Crawler supports scheduled recrawling, and sources such as Google Drive support webhooks. Define freshness by source rather than treating authorization as a guarantee of continuous real-time sync.

3.4 Supermemory is a product context API, not only an Agent library

Supermemory's strength is reducing integration work to API and connector surfaces. A product can send conversations, documents, URLs, or files to the platform, then ask profile and search for usable context. The tradeoff is that some internals remain hosted-service behavior: public materials show request parameters, response shapes, and processing states, but not every extraction, consolidation, or reranking policy.

The Supermemory local guide provides a single-binary entry point selected through the SDK baseURL. The v5 examples here require supermemory 5.x on npm or PyPI and supermemory-server v0.0.9 or later locally. Upgrade an older server before using namespace routes.

The local Memory API covers ingestion, search, and profiles, with extraction models configured by the operator. Connectors and hosted Supermemory MCP remain platform capabilities. The local binary is not open source, so data and model placement and the ability to modify knowledge processing are separate selection criteria. Changing the service address also does not migrate existing data.

4. Choose the route that matches the system

4.1 Start with the problem the system must solve

Cognee and Supermemory both make memory more platform-like, but they start from different questions. Cognee asks how raw material becomes a reusable knowledge layer. Supermemory asks how a product gets memory, profiles, search, connectors, and file processing through one API.

System pressure Natural route What to inspect first
You want an external memory layer between app and model, with write policy, decay, temporal reasoning, and retrieval ranking. Mem0 Write and retrieval algorithms.
Memory is part of agent state alongside persona, human profile, tools, and messages. Letta Agent state ownership and context compilation.
Facts change over time, and old facts need provenance rather than deletion. Graphiti Temporal graph and episode provenance.
Memory work affects the current execution path, so hot path tools and background managers must be separated. LangMem / LangGraph Hot path, background manager, store, and checkpointer.
Documents, code, expert patterns, or company knowledge need to become a reusable knowledge layer. Cognee add, cognify, search, datasets, graph/vector configuration.
A product needs memory, profiles, search, connectors, and file processing behind one API. Supermemory add, profile, search, connectors, and namespace boundaries.

The reusable lesson is to classify history before choosing infrastructure. Is this record evidence, a profile fact, a relationship, workflow state, a knowledge-layer artifact, or context for this turn only? Cognee and Supermemory push that question to platform scale, where the hard part is often not finding content, but making data sources, processing responsibility, retrieval contracts, and deletion boundaries explicit.
