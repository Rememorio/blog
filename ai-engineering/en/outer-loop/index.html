Loop Engineering: Connect Runs into a Work System

The agent loop answers how this run advances. The outer loop answers where work comes from, which run owns it, how results are verified, how failure hands off, and when retries stop. That is what turns a set of clever runs into an operable system.

Topic: Outer loopTime scale: across runsEvidence: official public material

A run may fix a bug in ten minutes or end because of context, budget, restart, or a human decision. The real work item often lives longer: an issue moves through investigation, implementation, CI, review, and repair; an incident through diagnosis, mitigation, and postmortem; a report gathers new data every day. The outer loop keeps those objects independent of one session’s accidental memory.

Reading contract

  • This part answers: how to manage work, ownership, verification, checkpoints, retries, and escalation across runs.
  • Terminology: “Loop Engineering” is this series’ operational label for outer-loop design; it is not presented as one standardized OpenAI or Anthropic term.
  • Exit check: you should be able to replace cron + prompt with work items, leases, idempotency, verifiers, and terminal states.

Evidence boundary

OpenAI’s Harness engineering describes Codex reviewing and iterating until checks are satisfied; the official 2026 Symphony specification shows an orchestrator watching a task board and launching agents for active work. Anthropic’s long-running harness and Managed agents material explains checkpoints, sessions, and progress across context windows. We abstract outer-loop mechanisms from those first-party sources, not a community label.

1. The outer loop owns a work item, not a chat

Chat is an interaction surface; a work item is an operational object. It needs a stable id, goal, done criteria, priority, dependencies, current owner, attempt, checkpoint, external references, and terminal state. A run is one execution instance assigned to that work item.

3. Triggers and selection need leases, not only queues

Webhooks duplicate, cron jobs overlap, workers crash, and completion messages disappear in network partitions. Without an ownership protocol, two agents can modify one item concurrently or a dead worker can hold it forever. A lease grants temporary ownership with expiry: the worker renews, releases on completion, and loses ownership when the lease expires.

  • Deduplication: identical external events create one work item.
  • Lease: one run owns exclusive writes; read-only investigation may use a separate parallel policy.
  • Heartbeat: distinguish a long run from a dead worker.
  • Fencing token: a late write from an old lease cannot overwrite the new owner.
  • Backpressure: launch according to resources, risk, and human review capacity.

4. Cross-run continuity needs a handoff, not merely a summary

Anthropic’s long-running harness experience emphasizes clear progress files, git state, and clean task slices so a later agent can continue. A handoff serves machines and people: structured fields make recovery testable; narrative preserves decisions and surprises; raw artifacts preserve evidence.

5. Retry budget belongs to the work item

An inner-loop tool retry is different from replaying an entire run. The latter costs more and can duplicate effects. Before every relaunch ask: what failed, what changes in the new run, have old effects been reconciled, and how much budget remains? “Try once more” is not a sufficient answer.

Persist retry budget with the work item so worker restarts do not reset it. Vary policy by class: transient infrastructure errors back off; authority blocks wait for approval; repeated invariant failures escalate; an uncertain external write reconciles before replay.

6. Idempotency and an effect ledger prevent duplicate worlds

Creating a PR, issuing a refund, or sending a notification can succeed while its response is lost. If the outer loop sees only a timeout, it may repeat the effect. Retriable effects need stable idempotency keys and a ledger of proposed, started, committed, and observed states. Recovery queries the world before continuing, compensating, or completing.

  • Record “the call happened” separately from “the world changed.”
  • Prefer external API idempotency; otherwise use a business key plus reconciliation query.
  • Model and audit compensating actions; not every effect is reversible.
  • Unknown effect state is reconciliation, not ordinary failed-and-retry.

7. People own judgment boundaries, not polling

OpenAI’s Harness engineering starts from scarce human attention. Put people at high-leverage boundaries: conflicting goals, high-risk authority, quality that cannot be automated, and decisions to spend more budget. An escalation package should be compressed but sufficient: what happened, what is verified, options and impact, recommendation, and deadline.

The outer loop turns runs into an operable work system. It still needs external truth for the “verify” step. The final part covers evals and feedback: measure outcomes, localize failures, and turn evidence into safe system change.
