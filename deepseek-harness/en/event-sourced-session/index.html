DeepSeek Harness source notes · Part III

What “Model-visible means logged” actually constrains

DSH stores immutable events, maintains a replaceable surface, and derives model history from it. UI, recovery, and the model read the facts each needs. Tool additions and removals also become messages, so later requests can reconstruct the capabilities available at that point.

Many agent systems begin with messages.push(). Tool state, tokens, approvals, retries, and UI progress then accumulate in adjacent maps; recovery eventually guesses which maps can be reconstructed from messages. DSH reverses the ownership: runtime facts enter an append-only log, and model messages are one projection over it.

One turn serves three consumers with different needs. The model needs canonical system, developer, user, assistant, and tool messages. A human timeline needs the original conversation and tool progress. Recovery also needs turn/step boundaries, request headers, errors, and lineage. Sharing one array guarantees that some consumer eventually receives too much or too little.

Reading contract.After this chapter, you should be able to explain what append() guarantees before and after commit; why five message event types require surfaceOp; why replace shadows the model surface without deleting raw history; why a human transcript must not read the current surface directly; and how unknown events, sourceEventSeqs, and session/end-seed make restoration fail more safely.

Source snapshot.This chapter follows 687f282. The logical format is v4. Session owns append, surface validation, and seed admission; the format catalog migrates historical generations and validates persisted data on read.

1. How Session appends and protects runtime facts

1.1 append snapshots, validates, then commits once

Session.append() never stores a caller's mutable object reference directly. It creates lossless JSON snapshots of data, surface metadata, and sourceEventSeqs; assigns continuous seq and time to a frozen candidate; then validates markers, provenance, and replacement coverage. SurfaceManager validates and plans the transition before the event enters the private log; the surface then advances over admitted events. A failed validation cannot leave half an event or half a replacement behind.

Events admitted by append() and their nested messages are deeply frozen. A caller cannot mutate a content block later and silently change model history. A change requires an explicit replacement or a logged message-projection decision handled by a registered interpreter. The former session.events interface is gone; snapshotEvents() still returns stable snapshots but is deprecated too. New production logic should consume query or projection interfaces rather than repeatedly scan the whole log.

This is a call-shape example: message and summary are constructed messages, endpoints are current-node SessionSeq values, and shadowedSeqs includes every replaced node.

session.append('user/message', message, {
  surfaceOp: 'append',
})

session.append('user/message', summary, {
  surfaceOp: { op: 'replace', startSeq, endSeq },
  sourceEventSeqs: shadowedSeqs,
})

1.2 Notification follows commit, and observer failures are contained

An attached Session emits session/event only after commit. Listener failures are contained independently: a telemetry or UI exception cannot remove an accepted event or prevent other observers from seeing it. Reentrant append is rejected so an observer cannot recursively disturb event ordering on the same notification stack.

A persistence listener may perform write-behind, but a producer that requires durability must explicitly await ctx.sessions.flush(session). Part IV covers that barrier. Session append owns the atomic in-memory fact; flush waits for external mirrors.

2. The event vocabulary separates content, execution, and diagnostics

2.1 Five message types enter the surface; streams settle separately

SurfaceEventType includes system/message, developer/message, user/message, assistant/message, and tool/result. All five require surfaceOp. The loop writes its first system node before the first user message. request/header retains call configuration, tool schemas, and adapter defaults, and rejects the retired header.system field. V4 tool results use a first-class role: 'tool' message: toolCallId and isError belong to the message, and content directly contains result blocks.

While an answer streams, the interface consumes live agent/assistant-stream frames. The log no longer appends one event per chunk. At settlement, successful output becomes assistant/message; a failed or retried attempt that committed no message becomes assistant/attempt. Both embed a stream preserving timing and delta boundaries. Cancellation may commit the delivered text or reasoning prefix with interrupted: true, excluding tool calls that were never dispatched.

Live frames reach the interface first, settlement events then enter Session, and flush waits for persistence. Attempts, turn/step boundaries, tool/call, and request records support recovery and diagnostics. A call record identifies the scheduler’s admission point; subsequent results and recovery checks establish the external execution state.

A simplified failed-then-successful request retry makes the three channels distinct:

Live display: attempt 1 frames → attempt 2 frames
Session: assistant/attempt { stream: … }
         assistant/message { message: …, stream: … }
Model history: only the committed assistant/message enters
Persistence: flush waits for those Session records to be written

2.2 Tool updates bind developer messages to historical definitions

Continue the test-repair example: the first step exposes read, and the next mounts search. The loop first records a new request/header containing complete read/search definitions, then appends a developer/message with a search tool-addition and headerSeq pointing to that header. A later schema change still leaves the original definition available for replay. Request construction compares names to emit additions and removals; tool history decides whether a same-name schema change restarts the declaration series.

This abbreviated record omits message ids, timestamps, and complete schemas:

seq 20  request/header
        header.tools = [read, search_v1]
seq 21  developer/message  surfaceOp: append
        headerSeq: 20
        message.role: developer
        message.content: [{ type: tool-addition, toolName: search }]
seq 30  developer/message  surfaceOp: append
        message.content: [{ type: tool-removal, toolName: search }]

Additions require an earlier headerSeq, with exactly one complete schema for each name in that header. Removal-only messages forbid the reference. Session validation enforces this during append, restore, and full-log folding. Tests retain the historical binding through later headers, replacement, restoration, and fork.

2.3 sourceEventSeqs connects a product to its inputs

system/message, developer/message, user/message, and tool/result can cite source events through sourceEventSeqs. A compaction replacement must cite every shadowed surface node; a tool-result rewrite cites the original result. References must be nonempty, unique, and earlier than the new event. assistant/message instead embeds its own raw stream and explicitly forbids top-level sourceEventSeqs; it no longer assembles provenance from chunk event numbers.

sourceEventSeqs identifies the events that produced a message or summary; headerSeq selects schemas for tool additions. Source references must cover every node shadowed by a replacement, while header references must point to request/header. Each relation receives its own validation.

3. Surface is the ordered projection of current model history

3.1 append extends the tail; replace shadows an inclusive range

SurfaceOp has only two shapes: 'append', or { op: 'replace', startSeq, endSeq }. Both endpoints must both be current surface nodes in the right order. The new event takes their position. Shadowed seqs leave surface.nodes but remain in SessionEvent[].

Each positional replacement increments both replaceGeneration and contentGeneration; a plugin content change that leaves nodes in place increments only the latter. Ordinary append keeps its incremental tail path, while deriveMessages() rebuilds against contentGeneration. Otherwise an unchanged node list could conceal stale model content.

The system prompt has an additional positional rule: when surface node 0 is a system/message, a replacement covering it must itself be a system event replacing exactly that one node. Later system nodes have no such protection. Whether a nonempty prompt update can append inside history depends on the currently bound route's systemPromptUpdate: 'in-history' capability and request series. Incapable routes normalize it at the first system node; clearing the prompt replaces every active system node with empty content. SystemPromptProjection performs these logged writes, rather than the UI editing text in place.

3.2 Human transcript and model surface deliberately differ

Suppose compaction shadows ten turns with one summary. The next model request should see the summary and newer messages, but a user who already saw those turns should not watch them vanish. Session therefore exposes isAppendSurfaceEvent(): a human transcript reads append-origin events, while replacement copies affect only the model-facing surface.

The original log retains all ten turns, while the surface contains the summary and newer messages. Human timelines read the original append events; model requests read the currently effective surface.

4. deriveMessages is a constrained incremental cache

4.1 Each new surface node projects once

deriveMessages() records the processed node count and contentGeneration. With that generation stable, it visits only the new tail and returns a fresh array of shared, deeply frozen Message objects. A later append cannot grow an array a caller already holds. Unchanged messages reuse original data; plugin projections create immutable derived copies while retaining message identity.

An empty-content assistant/message may retain max-token usage; an empty system/message records the absence of instructions at that position; an empty developer/message also retains its surface position. All three project to null. Direct prompts, synthetic injections, and goal rounds use user messages with typed source attribution. Producers write any necessary framing into content.

4.2 Content changes need a replayable plugin decision

Suppose a tool result keeps the same seq but a pruning plugin wants the model to read only part of its content. The plugin cannot mutate the original result. It declares a message-projection event and registers a pure interpreter with registerMessageProjection(). Session invokes it to validate the decision before acceptance, then caches immutable message updates that retain identity.

This leaves surface.nodes unchanged while invalidating the content cache. Missing interpreters reject append and restore; unloading an interpreter already used also blocks cached reads. Recording “pruning completed” is insufficient: recovery must be able to interpret exactly how that decision changed model messages.

4.3 “Model-visible means logged” is a bidirectional rule

  1. Model history derives from committed surface events.
  2. Logged content is not automatically model-visible; five message event types on the current surface supply messages, with logged content projections applied.
  3. System and developer messages come from the surface; current tools, provider/model configuration, and adapter defaults come from request/header. request/context records route capabilities but does not participate in header equality or request reconstruction, and cannot substitute for the current prepared call’s capabilities.

Tool declarations also have a separate toolHistory() cache. It folds headers and developer messages in event order, consuming only unseen records and resolving additions through historical headerSeq references. An explicit new series or a changed schema for a retained name rebuilds the declaration baseline; restoring the same name with the same definition preserves the series. Older logs with headers but no matching updates fall back to complete active declarations. Both loop and compaction requests use this state; adapters then choose their wire representation using the current route’s capabilities.

Experimental plugins can use appendPluginRecord() for plugin:<owner>/<record> records. They carry ignorable: true, remain in the log across resume and fork, require owner validation on read, and receive best-effort retention during format migration. They hold experimental state whose loss is acceptable and never enter the model surface.

5. Validate persisted history before constructing a restored Session

5.1 A seed must be a valid current-format prefix

Session.fromRestore() adopts independently owned or already deeply frozen seed events supplied by persistence. It validates runtime-required fields, event envelopes, continuous seqs, surface transitions, and headers without repeating a complete event copy/freeze pass. Embedded assistant streams remain for stream consumers or storage verifiers to inspect. Ordinary Session.create() seeds still take the snapshot path. Callers must honor the ownership contract rather than disguise shared mutable data as prepared restoration input.

An unknown event without ignorable: true refuses reconstruction, as does a message-projection event without its interpreter. Unknown ignorable records remain in the log without changing the surface: skipping interpretation does not mean deleting the record.

SESSION_FORMAT_VERSION is 4. The built-in catalog provides adjacent v0→v1→v2→v3→v4 migrations; storage retains the original generation and publishes a current-format successor. V3→V4 lifts nested tool results into tool-role messages, converts message sources, remaps event references, and validates the converted artifact. Future versions, missing migration routes, or unsupported historical structures refuse admission. Existing v4 logs go directly through current reader validation.

The V4 format layer enforces cross-event relationships: turn/step enclosure, tool request/result pairing, and retry coordinates are checked before the accepted log becomes visible. The JSONL scanner validates records before handling a recoverable tail. Session construction continues to check envelopes, sequence, surface, and interpreters; these read-path checks replace the former optional invariant companion.

5.2 How an exact fork prefix becomes a continuable child

buildForkSeed() copies the inclusive prefix ending at the selected seq, including a cut inside an open turn. It first appends session/end-seed { inherited: true } at the exact cut, fills missing tool results for the open step, and appends the required step/end and turn/end { reason: { kind: 'forked' } }. Previously closed steps and turns stay unchanged. inheritedEventCount counts only copied source events.

Parent prefix: turn/start → step/start → assistant/message → tool/call
Child additions: session/end-seed { inherited: true }
                 tool/result { TOOL_OUTCOME_UNKNOWN }
                 step/end → turn/end { reason: forked }

The synthetic result describes records inherited at the cut. The parent may execute or finish a call afterward, so both fork-generated TOOL_NOT_STARTED and TOOL_OUTCOME_UNKNOWN require read-only, idempotency, or external-state checks before retrying. Cut-point tests cover both missing call starts and calls without results. The current local subagent_fork implementation still selects the last completed-turn prefix; exact mid-turn cuts are a Session fork API capability.

The child owns its inherited marker and synthetic closers. firstLifecycleSeq starts at those child-owned records; firstLiveSeq is the entire seed length passed into construction, so these positions can differ for a new fork. Restoring an existing Session retains its inherited cut and adds an ordinary lifecycle marker when needed. Independent brackets such as compaction use markers to identify unmatched starts from an earlier lifecycle.

6. Engineering consequences of the model

  1. Reconstruct history from Session.UI may consume more events, but recovery and model history return to Session.
  2. Append replayable content changes.Changing nodes means a replacement with provenance; changing content alone means a replayable plugin-projection decision.
  3. Derive messages by event type.Boundaries, failed attempts and their streams, usage, and headers support recovery and diagnostics.
  4. Build timelines from original append events.Retain the conversation the user has already seen while model requests read the compacted current surface.
  5. Default unknown events to required.Over-refusal costs an upgrade; silent skipping may continue execution from a gutted state.

Part IV connects this append-only log to process and external effects: write-behind, flush checkpoints, approval, sandboxing, and crash repair determine whether a tool call can safely continue.
