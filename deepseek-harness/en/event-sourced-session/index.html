What “Model-visible means logged” actually constrains

Session is not another name for a message array. DSH first stores immutable events, maintains a replaceable surface over them, and only then derives model history. UI, recovery, and the model can share facts without sharing one view.

Many agent systems begin with messages.push(). Tool state, tokens, approvals, retries, and UI progress then accumulate in adjacent maps; recovery eventually guesses which maps can be reconstructed from messages. DSH reverses the ownership: runtime facts enter an append-only log, and model messages are one projection over it.

One turn serves three consumers with different needs. The model needs canonical user, assistant, and tool messages. A human timeline needs the original conversation and tool progress. Recovery also needs turn/step boundaries, request headers, errors, and lineage. Sharing one array guarantees that some consumer eventually receives too much or too little.

Reading contract.After this chapter, you should be able to explain what append() guarantees before and after commit; why only three event types carry surfaceOp; why replace shadows the model surface without deleting raw history; why a human transcript must not read the current surface directly; and how unknown events, sourceEventSeqs, and session/end-seed make restoration fail more safely.

Evidence boundary.This chapter is pinned to b150a55. The root Session package always owns snapshotting, freezing, surface validation, and seed acceptance; persistence is a separate plugin. The source proves the in-memory and reconstruction contracts, not that a custom backend implements durability correctly.

1. Session is an append-only fact source, not an editable transcript

1.1 append snapshots, validates, then commits once

Session.append() never stores a caller's mutable object reference directly. It creates lossless JSON snapshots of data, surface metadata, and sourceEventSeqs; validates markers, provenance, and replacement coverage; then assigns continuous seq and time. SurfaceManager plans the transition before the log and surface commit together.

Accepted events and nested messages are deeply frozen, and session.events returns a cached frozen snapshot. A caller cannot mutate a content block later and change model history without an event. Changing the current model surface requires a new, explicit replacement event.

session.append('user/message', message, {
  surfaceOp: 'append',
})

session.append('user/message', summary, {
  surfaceOp: { op: 'replace', start, end },
  sourceEventSeqs: shadowedSeqs,
})

1.2 Notification follows commit, and observer failures are contained

An attached Session emits session/event only after commit. Listener failures are contained independently: a telemetry or UI exception cannot remove an accepted event or prevent other observers from seeing it. Reentrant append is rejected so an observer cannot recursively disturb event ordering on the same notification stack.

A persistence listener may perform write-behind, but a producer that requires durability must explicitly await ctx.sessions.flush(session). Part IV covers that barrier. Session append owns the atomic in-memory fact; flush waits for external mirrors.

2. The event vocabulary separates content, execution, and diagnostics

2.1 Only three event types can enter the model surface

SurfaceEventType is a strict union of user/message, assistant/message, and tool/result. Each stores a complete identified Message and must carry surfaceOp. deriveEventMessage() returns that frozen value; it does not invent a new id, role, or framing layer.

Other events answer runtime questions rather than conversation content. Turn and step events delimit lifecycle; assistant/chunk retains stream provenance and usage; tool/call proves execution began; request/header captures the non-history request envelope. They remain in the log but project to null, so provider history stays clean.

2.2 sourceEventSeqs connects a product to its inputs

An assistant/message may cite the chunks that formed it. A compaction replacement must cite every shadowed surface node. A tool-result rewrite cites the original result. References must point to unique earlier seqs, and replacement provenance cannot omit any node in its declared range.

This is not a general DAG engine. It is a narrow provenance seam: when raw sources and canonical products coexist, an auditor can identify what produced a message or summary, and reconstruction can reject an incomplete replacement claim.

3. Surface is the ordered projection of current model history

3.1 append extends the tail; replace shadows an inclusive range

SurfaceOp has only two shapes: 'append', or { op: 'replace', start, end }. Start and end must both be current surface nodes in the right order. The new event takes their position. Shadowed seqs leave surface.nodes but remain in SessionEvent[].

Every positional replacement increments replaceGeneration. An ordinary append does not invalidate prior message projection; a middle rewrite does. deriveMessages() clears and rebuilds its cache only when the generation changes, preserving a cheap incremental path for normal conversation.

3.2 Human transcript and model surface deliberately differ

Suppose compaction shadows ten turns with one summary. The next model request should see the summary and newer messages, but a user who already saw those turns should not watch them vanish. Session therefore exposes isAppendSurfaceEvent(): a human transcript reads append-origin events, while replacement copies affect only the model-facing surface.

Compaction is not conversation deletion. The log remains the historical fact source; surface answers “what should be sent now,” not “what has ever happened.”

4. deriveMessages is a constrained incremental cache

4.1 Each new surface node projects once

deriveMessages() records the processed node count and generation. With a stable generation it visits only the new tail and returns a fresh array of shared, deeply frozen Message objects. A later append cannot grow an array a caller already holds.

An empty-content assistant/message may exist only to retain max-token usage, so it projects to null. Direct prompts, synthetic injections, and goal rounds are all user messages; their typed source preserves provenance instead of projection adding ambiguous string wrappers.

4.2 “Model-visible means logged” is a bidirectional rule

  1. Content entering model history must be a committed surface event; a local prompt buffer is not durable history.
  2. Logged content is not automatically model-visible; only three message event types on the current surface project.
  3. System text, tools, provider, and adapter defaults belong to request/header and reconstruct outside history, so logging does not duplicate their tokens.

5. Restoration rejects an invalid world instead of merely parsing JSON

5.1 A seed must be a valid current-format prefix

Session.fromRestore() detaches, snapshots, and validates header and seed: ids match, seqs are continuous, data is lossless JSON, surface transitions are legal, assistant messages retain provider/model provenance, and request headers identify provider/model. An unknown event without ignorable: true refuses reconstruction rather than assuming it cannot affect later meaning.

SESSION_FORMAT_VERSION remains pre-release version 0, and Session accepts current shapes only. Narrow compatibility conversion belongs at the persistence read boundary. This sacrifices “open anything” in favor of never continuing side effects from a falsely reconstructed history.

5.2 session/end-seed separates restored history from this lifecycle

After a resume or fork seed is accepted, the constructor appends session/end-seed. It is a positional boundary, not a liveness heartbeat: earlier records came from the seed; later ones belong to this live lifecycle. Independent brackets such as compaction can tell whether an unmatched start belongs to a prior crash tail or current work.

The invariant companion also replays sequence, turn/step enclosure, and same-step tool pairing. The root package always enforces structural and surface validity; the companion adds execution relationships. Neither substitutes for the other.

6. Engineering consequences of the model

  1. Do not make a UI store authoritative.UI may consume more events, but recovery and model history return to Session.
  2. Do not edit messages in place.Changing the current model surface means appending a replacement with provenance.
  3. Do not feed the raw log to the model.Boundaries, chunks, usage, and headers are recovery facts, not conversation messages.
  4. Do not render human history from the current surface.It correctly hides compacted nodes and would therefore erase visible conversation.
  5. Default unknown events to required.Over-refusal costs an upgrade; silent skipping may continue execution from a gutted state.

Part IV connects this append-only log to process and external effects: write-behind, flush checkpoints, approval, sandboxing, and crash repair determine whether a tool call can safely continue.
