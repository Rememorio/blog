Claude Code Source Notes · Part VII

How Claude Code isolates subagents and forked work

A subagent is not another chat window. Claude Code creates a separate ToolUseContext with its own prompt, tools, transcript, and query loop. A fork takes a different route: it deliberately copies the parent's request prefix so the child can reuse the prompt cache.

Project: Rememorio/claude-code Topic: subagents and fork Scope: public mirror and official docs

The AgentTool path starts when the model asks to delegate work. From the parent loop's point of view, this is still a tool call. If it is accepted, Claude Code selects an agent, decides which tools that agent may use, creates separate state, and runs a child query loop.

Reading goal: distinguish a normal subagent from the fork path. The normal path rebuilds a focused prompt and tool list; the fork path keeps the parent's system prompt, tools, thinking settings, and message prefix as stable as possible.

1. AgentTool chooses a concrete execution path

The input schema contains a task description and prompt, plus optional fields such as subagent_type, model, and background execution. When the related features are enabled, it may also accept a teammate name, team name, permission mode, isolation choice, and working directory. These fields decide how and where work runs; they do not create a free-form chat.

The code first separates teammate spawning, the fork path, and a named agent definition. It then applies Agent(name) deny rules. An agent definition may also require MCP servers; Claude Code waits for pending servers for a limited time and stops with an actionable error if their tools never become available. The child starts only after the tools promised by its definition are actually present.

2. A normal subagent gets a rebuilt tool list

The normal path does not copy the parent's tool array verbatim. It starts from the current permission state and MCP tools, selects the agent's permission mode, and calls assembleToolPool(). resolveAgentTools() then removes tools forbidden to all agents, custom agents, or background agents, and applies the definition's tools and disallowedTools lists.

MCP tools are generally available to agents unless another rule removes them. A non-main-thread Agent tool is filtered out to prevent unbounded nesting. The normal child also receives a system prompt generated from its selected agent definition, environment details, and enabled tools rather than a copy of the parent's rendered prompt.

3. The fork path preserves the parent request prefix

The fork path makes a different tradeoff. It inherits the parent's rendered system prompt and uses buildForkedMessages() to clone the relevant assistant message, placeholder tool results, and a directive for the child. It also enables useExactTools and passes the parent's exact tool list.

This exactness matters because tool definitions and thinking configuration contribute to the prompt-cache key. Rebuilding tools with a different permission mode could invalidate the cache at the first changed schema. Fork children therefore inherit the parent's thinking configuration as well. The Agent tool remains in the exact schema list, but a runtime check rejects another fork when the current request is already a fork child, preventing recursive branching.

4. createSubagentContext isolates mutable state

createSubagentContext() defaults to separating mutable state unless the caller explicitly shares it. It clones file-read state, creates fresh memory and dynamic-Skill trigger sets, assigns a new agent id and tracking depth, and replaces parent UI callbacks such as setToolJSX and addNotification with no-ops.

A synchronous interactive subagent may share selected callbacks, response accounting, and an abort controller with its parent. A background subagent is more isolated. When it has no shared interactive controller, its application state sets shouldAvoidPermissionPrompts: true, so unanswered permission requests are handled by hooks or denied instead of waiting for an unavailable dialog.

5. runAgent operates a complete child query loop

runAgent() is an asynchronous generator, not a single provider request. It creates child state, runs SubagentStart hooks, registers hooks declared in the agent frontmatter, preloads Skills as messages, connects agent-specific MCP servers, and then enters query(). Child messages are written to a sidechain transcript as the loop continues.

A synchronous agent yields progress records to the parent and eventually returns a tool result. A background agent registers a task and reports completion through a notification or task result. Both paths have their own agent id, transcript, and cleanup behavior; neither is hidden code still running inside the parent turn.

A useful mental model is a child runtime with explicit inputs and outputs. Claude Code selects an agent, calculates its tools, chooses isolated or forked state, runs a separate query loop, records a transcript, and returns progress or a result to the parent.
