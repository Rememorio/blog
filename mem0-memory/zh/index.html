Mem0 记忆算法怎么演进：从可更新记忆、图关系，到 ADD-only 写入与多信号检索

Mem0 不是一开始就只追加记忆。论文里的 mem0 先让 LLM 对旧记忆做 ADD、UPDATE、DELETE、NOOP 判断； mem0g 又把实体和关系放进图数据库；到 2026 年 4 月的 v3，路线才转向 single-pass ADD-only、实体索引和多信号检索。 这篇文章先讲这条算法演进，再解释 Temporal Reasoning 与 Memory Decay 为什么自然接在后面。

项目：mem0ai/mem0 主题：agent memory 范围：公开源码与官方文档可见边界

先看一个很普通的长期记忆场景。用户一月说自己喜欢素食餐厅，三月说最近开始吃海鲜，六月又问“我以前约朋友吃饭一般选什么地方？”。 如果系统只保留最后一条偏好，就会丢掉一月的历史；如果系统把所有事实都无差别塞进上下文，又会让模型把过时偏好当成现在偏好。 真正的问题不是“要不要记住”，而是：历史应该怎样保存，现在是否仍然适用又该在哪一层判断。

Mem0 官方博客从几个角度反复强调同一件事： context window 更像 RAM，不是长期存储； 更大的上下文窗口也不能替代持久记忆； 把记忆写成一个文件又会把证据、偏好、临时状态和检索策略糊在一起。 这些文章是理解 v3、Temporal Reasoning 和 Memory Decay 的入口：它们不是几个孤立功能，而是在回答同一个长期记忆问题。

证据边界。 本文把事实分成四层：Mem0 原始论文说明 paper mem0 与 mem0g 的算法设计； Mem0 官方博客和文档说明 Platform v3 的公开合约； mem0ai/mem0 公开源码说明 OSS 与 Python SDK 可见的调用路径； Platform 服务端内部实现不可见，因此 Temporal Reasoning 和 Memory Decay 的排序细节只按官方合约描述，不写成源码事实。

读这篇文章可以带着五个问题：

  1. 口头说的 v1、v2、v3，和论文里的 mem0、mem0g 是不是一回事？
  2. paper mem0 为什么要让 LLM 判断 ADD、UPDATE、DELETE、NOOP？
  3. mem0g 为什么把实体和关系放进图数据库，又带来了什么成本？
  4. v3 为什么改成 ADD-only、实体索引和 hybrid retrieval？
  5. Temporal Reasoning 与 Memory Decay 分别把“时间”和“近期使用”放到了哪一层？

一、先看三代算法怎么一路改过来

公开材料没有把这三步直接叫作“v1、v2、v3”：论文里叫 mem0 和 mem0g，迁移材料里讲 mem0 v3。 更合适的读法，是把它们看成三次算法取舍：基础 mem0、图版本 mem0g、以及 v3。 如果只从 v3 的 ADD-only 看起，Mem0 很容易被误解成“只是不覆盖旧记忆”。实际变化更像三步： 先用 LLM 维护一组较小的记忆，再显式引入图关系，最后把写入变简单，把更多判断交给检索和排序。 这三步各自解决一个问题，也各自暴露出新的成本。

称呼 更准确的读法 不要误读成
paper mem0 论文里的基础算法：抽取新 memory，再对相似旧 memory 判定 ADD/UPDATE/DELETE/NOOP。 官方产品里的“v1”。公开材料没有这样命名。
paper mem0g 论文里的图增强算法：显式抽 entity 和 relationship，并使用图数据库。 官方产品里的“v2”。它更像 mem0 旁边的一条 graph 变体。
v2 API / SDK 迁移材料里说的旧版本面：add 可能返回 ADD/UPDATE/DELETE，且有 enable_graph、graph_store 等图记忆配置。 单指 mem0g。v2 是产品/API/SDK 行为集合，不是论文算法名。
mem0 v3 2026 年 4 月后的新算法面：single-pass ADD-only、内置 entity linking、hybrid retrieval、Temporal Reasoning 和 Memory Decay。 只是把 mem0g 改名。v3 同时改了写入、图关系承担方式和检索排序。

1.1 paper mem0：先抽取，再决定怎么改旧记忆

先不要急着看 v3。把 原始论文里的 mem0 当成一个写入算法， 它的输入不是单条用户消息，而是一小段对话状态：最新 user/assistant message、之前的 summary、最近若干条消息，以及已有 memory。 算法可以简化成下面这个流程： 

输入：
  最新 user message + assistant message
  之前的 summary
  最近 m 条消息
  已有 memory store

写入：
  1. LLM 从新对话里抽取 k 条 candidate memory
  2. 对每条 candidate，用 embedding / vector similarity 在已有 memory 里召回相似的 m 条
  3. LLM 比较 candidate 和相似旧记忆
  4. 输出 ADD / UPDATE / DELETE / NOOP
  5. 按输出修改 memory store

读取：
  query -> vector similarity -> top memories -> 放回本轮上下文

这里的“相似”要分两层看。第一层是召回：candidate 会被转成 embedding，再和已有 memory 的向量做相似度搜索， 找出最值得比较的旧记录。第二层才是裁决：相似旧记录只是被拿给 LLM 看的候选项，并不表示分数高就一定 UPDATE。可见 OSS 代码里的 DEFAULT_UPDATE_MEMORY_PROMPT 也把这一步写成“比较新事实和已有 memory，然后选择 ADD、UPDATE、DELETE 或 NONE”。这里的 NONE 可以理解成论文和本文里的 NOOP：不修改。

新事实和旧 memory 的关系 应该怎么处理 直觉例子
旧 memory 里没有这个事实 ADD 旧：用户是工程师；新：用户叫 John。
同一事实，只是换了说法 NOOP / NONE 旧：喜欢 cheese pizza；新：loves cheese pizza。
同一对象或偏好，但新信息更具体，或者值已经改变 UPDATE 旧：喜欢打 cricket；新：喜欢和朋友一起打 cricket。
新事实否定旧事实，或者明确要求删除 DELETE 旧：喜欢 cheese pizza；新：不喜欢 cheese pizza。

这套做法的优点是 memory set 比较紧凑：相关事实可以合并，明显过时或错误的内容也能删掉。 但它不是严格去重算法：如果 embedding 没召回正确的旧 memory，或者 LLM 把“同义重复”误判成新事实， 系统仍然可能重复 ADD。缺点也来自同一个地方：写入阶段要让 LLM 做一次“新旧记忆裁决”， 而 UPDATE 和 DELETE 会削弱历史证据。用户后来问“去年我为什么改变偏好”时，被改写或删除的版本未必还在。 这就引出后面的核心问题：长期记忆到底应该在写入时整理成一个最新状态，还是先把历史留下来？

1.2 paper mem0g：在记忆旁边加一张关系图

mem0g 解决的是另一个痛点：单条文本记忆和向量相似度不擅长表达“谁和谁有什么关系”。 所以它不是只维护一组 memory records，而是在记忆旁边维护一张图。 

输入：
  对话消息
  已有 memory store
  graph store

写入：
  1. 从消息中抽取可记忆事实
  2. 显式抽取 entity 和 relationship
  3. memory 写入向量存储
  4. entity / relationship 写入图数据库

读取：
  query -> 找相关 memory
        -> 抽取 query entity
        -> 在图里找相关节点和关系
        -> 合并文本记忆与图结果

这让多跳关系更自然。比如用户在某家公司、某个项目、某位同事之间反复切换话题时，图结构更容易把这些关系串起来。 但代价是系统复杂度上升：要维护图存储，要处理实体合并和关系更新，还要让检索同时理解向量结果与图结果。 更关键的是，图数据库能表达关系，但不自动回答“哪条历史在当前问题下更该被使用”。

1.3 mem0 v3：只追加写入，把“当前该信什么”留给检索

走到 v3 时，Mem0 要解决的不只是“写得更快”。paper mem0 的写入路径像一次状态裁决： 它既要抽取新事实，又要判断旧事实是否该被合并、覆盖或删除。mem0g 再引入图关系后， 写入还要维护实体、关系和图存储。问题在于，长期记忆里的很多事实不是绝对对错， 而是随时间和问题视角变化：用户曾经喜欢 A，后来改成 B；问“现在喜欢什么”和问“为什么改变”需要不同历史。

所以 v2 到 v3 迁移文档 和 Token-Efficient Memory Algorithm 文章 里说的 single-pass ADD-only，可以理解成一次责任重分配：写入阶段负责提取新的记忆证据、连接相关旧记忆、写入可检索索引； “当前该信哪条”“过时事实还要不要进入 model view”则交给检索、时间和衰减信号处理。 

输入：
  对话消息
  existing memories
  可选 timestamp

写入：
  1. 单次 LLM 调用抽取新 memory
  2. 不对旧 memory 做 UPDATE / DELETE
  3. 用 linked_memory_ids 连接相关旧 memory
  4. batch embedding + hash 去重 + vector insert
  5. 记录 history ADD，并做内置 entity linking

读取：
  query -> semantic candidates
        -> BM25 keyword signal
        -> entity boost
        -> time / decay signals
        -> ranked model view

这不是说旧事实永远不能删，也不是说重复永远不会出现。它真正保护的是两件事： 写入阶段少做不可逆判断，历史变化先留下来；读取阶段再按当前问题选择模型应该看到的少量记忆。 这个选择让 v3 的后续机制有了位置：写入负责留证据，读取负责排顺序，Temporal Reasoning 负责时间视角，Memory Decay 负责近期使用信号。

1.4 先把三层对象分清：窗口、记录和模型视图

继续往下看源码和 Platform 功能前，要先分清三个对象。context window 是本轮模型能看到的工作区； memory record 是持久化后可检索的事实；model view 是检索之后放回本轮上下文的少量结果。 ADD-only 改的是 memory record 的写入方式，不是把全部历史塞进 context window；Temporal 和 Decay 改的是 model view 的选择方式， 也不是在存储层把旧事实抹掉。

术语 本文含义 常见误读
context window 本次请求发给模型的工作区，适合短期推理和工具结果。 把窗口变大当成长期记忆，忽略成本、遗忘和 lost-in-the-middle。
memory record 从对话中抽出的持久事实，带 payload、metadata、embedding 和历史记录。 把它当成“当前真相”，忽略它也可能是过去某一刻的真相。
model view 检索、过滤、排序后被展示给模型的少量记忆。 把它等同于全部历史，导致没召回的事实被误判为不存在。
ranking layer 把语义、关键词、实体、时间和访问历史转成当前结果顺序的层。 把排名结果当成写入覆盖的结果。

后续博客共同讨论的是 model view 质量

Mem0 的 BEAM benchmark 文章 和 memory simulation guide 都在强调生产记忆评测不能只看“有没有召回”。更关键的是过时事实、矛盾事实、时间条件和检索漂移。 Temporal Reasoning 和 Memory Decay 正是在这个问题空间里出现的：它们让系统在保留历史的同时，更清楚地回答“现在、当时、最近常用”。

二、写入为什么只 ADD：把状态裁决从写入阶段拿掉

旧写法的问题不是 UPDATE 一定错，而是它把一个长期问题压成了写入时的一次判断： 新事实和旧事实到底是重复、补充、冲突，还是不同时间点的真相？这个判断一旦落成覆盖或删除，后面再想解释历史就变难。 v3 的取舍是先把写入变成证据追加，再让读取阶段根据问题来选。

Mem0 的 Token-Efficient Memory Algorithm 文章给出 single-pass ADD-only 的方向，公开 OSS 路径也能看到同样的形状： Memory.add() 先处理输入、过滤器和 metadata，再进入 _add_to_vector_store()。 在这条可见路径里，LLM 提取的是新 memory，后续经过 batch embedding、hash 去重、vector insert、history ADD 和 entity linking。

旧路线的压力 ADD-only 的处理 得到的优势
写入时误判 UPDATE / DELETE 新事实作为新记录进入 memory store。 减少不可逆覆盖，保留之后解释历史的证据。
同一偏好在不同时间有不同答案 变化本身成为记忆，并可带时间信号。 “现在是什么”和“当时是什么”不再抢同一条记录。
图关系带来额外存储和维护成本 用 linked_memory_ids 和内置 entity linking 保留关联。 仍能表达相关性，但不要求 OSS 用户维护外部 graph store。
写入链路越长，成本和延迟越难控 单次抽取、batch embedding、hash 去重后写入。 写入路径更短，失败面更小，后续判断集中到检索层。

2.1 LLM 只做抽取和连接，不做最终状态裁判

ADDITIVE_EXTRACTION_PROMPT 把 LLM 的职责收在几件事上：抽取来自新消息的可记忆事实，用户和 assistant 消息都可能包含信息；相对时间要用 observation date 落到具体日期； 与旧记忆相关时使用 linked_memory_ids，而不是让模型直接改写旧记录。 

{
  "memory": [
    {
      "id": "0",
      "text": "User switched from almond milk to oat milk lattes after developing an almond sensitivity",
      "linked_memory_ids": ["existing-memory-id"]
    }
  ]
}

下面这个简化例子说明了关键点：变化本身会成为一条新的、可追溯的事实。旧偏好没有被静默删除； 后续检索可以同时看到“曾经喜欢什么”和“后来为什么变了”。这比覆盖更适合长期 agent，因为用户之后可能问的是历史，而不是当前偏好。

2.2 OSS 对 Platform-only 时间参数保持硬边界

公开源码里还有一个需要守住的边界： Memory.add(timestamp=...) 在 OSS 路径会直接抛出 Platform-only 错误； Memory.search(reference_date=...) 也一样。 这不是实现细节缺失，而是 API 层明确把 Temporal Reasoning 切到 Platform v3。 文章后面讨论 Temporal 时，只能把它当成官方 Platform 合约，而不能把服务端内部排序算法补成源码事实。

三、读取为什么要混合排序：只追加之后，选择发生在 model view

ADD-only 会让 memory store 保留更多历史版本和相关事实。如果读取仍然只是一次向量 top-k， 系统就容易把“语义相似”误当成“当前应该使用”。例如旧偏好和新偏好都和 query 很像，但它们回答的是不同时间点的问题。 所以 v3 路线把写入阶段拿掉的选择，放到了 model view 形成阶段。

Mem0 OSS 的搜索路径从 Memory.search() 进入 _search_vector_store()： 先做 query lemmatization 和实体抽取，再做 embedding；语义召回会 over-fetch，关键词搜索会生成 BM25 分数，实体 store 会给相关 memory 加 boost。 最后这些信号进入 score_and_rank()。

3.1 先用语义守门，再融合关键词和实体

score_and_rank() 里有一个容易忽略的顺序：semantic score 低于 threshold 的候选会先被排除， 之后才把 normalized BM25 和 entity boost 加进来。这意味着关键词或实体信号可以帮助排序，但不能把一个语义完全不相关的候选带进结果。 这个门槛保护的是 model view 的基本相关性。 

semantic candidates
  -> threshold gate
  -> add normalized BM25 when available
  -> add entity boost when available
  -> normalize by active signal budget
  -> return top_k

3.2 当前是否适用，需要时间和访问信号

一旦写入不覆盖，读取层就必须处理冲突和新旧关系。一个用户可以先说喜欢 A，后来改成 B； memory store 里最好同时保留两条，因为它们分别回答不同问题：“你现在偏好什么？”和“你以前为什么改变？”。 纯向量检索通常只知道文本相似，而 Temporal Reasoning 和 Memory Decay 让检索层拥有更多判断“现在是否仍然适用”的信号。

四、Temporal Reasoning：给检索一个时间视角

上一章留下了一个问题：如果旧事实和新事实都被保留，系统怎么知道这次 query 要站在哪个时间点回答？ 这正是 Temporal Reasoning 的位置。它不是把旧记录改成新记录，而是让写入记录“何时观察到这个事实”， 让搜索表达“以哪一天为观察点”。Temporal Reasoning 官方文章 和 文档 给出的公开合约包括：Platform v3 支持，默认启用； 写入可以带 timestamp；搜索可以带 reference_date；返回 shape 仍是普通 search 结果。

4.1 请求形态：写入时间和观察时间分开

Python SDK 的 Platform client 会把 add/search 请求发到 v3 endpoint： /v3/memories/add/ 和 /v3/memories/search/。 源码可见的是请求 shape 和参数转发；时间推理怎么在服务端参与 ranking，不在公开源码里。 

# Platform shape, simplified
client.add(
    messages=[{"role": "user", "content": "I switched to oat milk."}],
    user_id="u1",
    timestamp="2025-03-08T09:30:00Z",
)

client.search(
    "What milk did I prefer in February?",
    filters={"user_id": "u1"},
    reference_date="2025-02-28",
)

这里最重要的设计不是多了两个字段，而是把“事实发生时间”和“问题观察时间”分开。 timestamp 描述记忆何时进入历史；reference_date 描述这次检索要站在哪个时间点回答。 这让“现在是什么”与“当时是什么”不再争抢同一条覆盖记录。

4.2 Temporal 解决的是矛盾历史，不是替代过滤器

Temporal Reasoning 不是普通 metadata filter。filter 更像是先限定范围，例如某个 user、agent、run 或业务属性； temporal query 则是在已召回的历史中理解时间关系。比如“过去三个月有哪些变化”和“去年我更喜欢什么”都需要保留多条历史， 而不是只保留最新事实。

五、Memory Decay：用近期使用调整排名，而不是清理存储

时间视角解决的是“何时为真”，但还不够。长期 agent 会积累很多都相关、都没过期的事实； 如果某类信息最近反复被使用，它通常更应该进入当前 model view。这个问题不能靠删除旧记忆解决， 因为旧记忆以后仍可能在别的问题里有用。 Memory Decay 官方文章 和 文档 把它定义在 search-time soft re-ranking：不删除记忆，不在写入时改写事实，而是在候选集通过基础阈值之后，对排名做温和调整。

5.1 项目开关只改变 search-time ranking

公开 SDK 里能看到项目设置层面的开关： project.update(decay=True) 会把 decay 写入项目更新 payload。源码注释也把它限定为 search-time ranking：最近使用的记忆被 boost，stale 记忆被轻微压低； 关闭时恢复到 pre-decay behavior。具体访问历史的服务端记录和计算不在公开 OSS 路径里。 

# Platform project setting, simplified
client.project.update(decay=True)

5.2 关键边界：先相关，再衰减

Memory Decay 的几个边界决定了它不会变成“谁最近用过谁就赢”：它只适用于 Platform v3；会在比最终 top-k 更大的候选池上工作； 基础相关性 threshold 先执行，decay multiplier 后执行；公开返回的 score 会被 clamp 到常规范围；访问历史强化是异步的。 文档还给出量级边界：候选池会扩成 top_k * 3 且至少 50 条，decay multiplier 夹在 0.3x 到 1.5x。 这些细节都在保证一件事：decay 是排名偏置，不是事实删除。

边界 含义 避免的误读
search-time 候选被召回后再调整排名。 不是写入时把旧记忆衰减成别的事实。
threshold first 基础语义相关性先过门槛。 不是让频繁访问的无关记忆进入结果。
soft multiplier 近期访问上调，长期不用下调。 不是 TTL，也不是自动删除。
project opt-in 通过项目设置启用。 不是所有 Mem0 使用都会自动开启。

六、把几层合起来：旧事实不覆盖，新问题有视角

现在可以回到开头的问题。用户偏好从 A 变成 B，不应该简单覆盖 A； 因为系统以后可能需要回答“现在更可能是什么”，也可能需要回答“什么时候从 A 变成 B”。ADD-only 保留变化证据； hybrid retrieval 负责形成候选池；Temporal Reasoning 让查询带上时间视角；Memory Decay 让近期使用历史影响结果顺序。

6.1 什么时候靠 Mem0，什么时候靠应用层

Mem0 解决的是 agent memory 的大部分检索和个性化问题，但不是所有强一致状态都应该交给记忆系统。 支付地址、权限状态、合规开关、医疗禁忌这类必须强一致的事实，应该由业务数据库和应用层规则拥有； Mem0 可以帮助模型解释和召回上下文，但不应该成为最终授权来源。

信息状态 适合机制 为什么要这样做 会在哪些地方失效
偏好发生变化 ADD-only 记录变化，Temporal query 判断时间视角。 保留“以前”和“现在”的证据。 只保留最新值会丢历史，只保留旧值会答错当前。
近期反复使用 Memory Decay 对 search result 做软排名。 常用信息更容易进入当前模型视图。 它不能替代业务优先级和强规则。
必须精确执行 应用层数据库、权限系统或显式规则。 不让概率检索决定必须精确的状态。 把授权、支付、医疗判断放进 memory 会有风险。
长期稳定背景 普通 memory record 与 hybrid retrieval。 减少重复提问，保持个性化上下文。 如果缺少 filters，跨用户或跨 agent 边界会混乱。

6.2 一句话总结 Mem0 的路线

Mem0 最值得借鉴的地方，不是把“记忆”做成一个更大的上下文，而是把几件事分开放： 写入保留证据，检索形成候选，时间解释历史视角，衰减表达近期使用，应用层负责强一致规则。 这套分层让 agent 不必在“覆盖旧记忆”和“永远展示全部历史”之间二选一。
