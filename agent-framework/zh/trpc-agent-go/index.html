tRPC-Agent-Go 把 Go agent 做成服务端 runtime

一个客服 Agent 从网页接单，查询日志和工单，生成文件，等待用户第二天回来，还要记得此前进度。 tRPC-Agent-Go 把这些生产责任组织成一套 Go 服务端 runtime；本文先沿 Runner、Agent、Model 这条执行主干看完整框架，再重点拆 Rememorio 推进最集中的 summary 与 memory。

主题：tRPC-Agent-Go 主干：Runner / Agent / Model 服务：Session / Memory / Artifact 重点：summary / memory / session_load

阅读契约。 这篇先回答三个问题：谁建立并收尾一次 run，谁决定这一轮怎样执行，谁只负责根据请求生成下一步。 读完以后，你应该能把 Runner、Agent、Model 放回正确调用顺序，并说明 Session、Memory、Artifact、Tool、 CodeExecutor、Graph 和协议 adapter 分别接在哪一侧。

证据边界。 源码链接固定到公开快照 d3b50fd90d60b4ece8a78e89cf890a4f06d78235。 文中“owner”“主干”“账本”“投影”是工程归纳；直接行为以公开源码中的 runner、agent、model、session service、 event、memory、artifact、tool、graph、evolution、server 和 processor 为准。

一、先看一个客服 Agent 上线后会遇到什么

假设一个企业客服 Agent 要帮用户排查线上错误。它先读取日志，再查询历史工单，必要时运行诊断代码， 最后生成一份报告。只调用一次模型并不难，困难的是把这件事连续、可靠地做完。

请求可能来自网页，也可能来自另一个 Agent；日志查询和代码执行会产生副作用与文件；确定性排查步骤不能全靠模型临场发挥； 服务重启后要继续原任务；第三天用户只说“还是昨天那个错误”，系统还要找回必要背景。tRPC-Agent-Go 的框架边界， 就是把这些“模型之外”的生产责任接进同一条运行主线。

二、先抓住三层主干：Runner、Agent、Model

如果把 package 名都摆在同一排，最容易把 Event、Session、Tool、Graph 和 Agent 误当成平级“角色”。 更清楚的读法，是先沿调用方向抓住三层主干，再把服务和组件挂回它们真正出现的位置： 

请求边界
  -> Runner：建立 run、选择 Agent、挂载服务、收集结果
       -> Agent.Run(invocation)：决定这一轮怎样执行
            -> Model.GenerateContent(request)：生成文本或 tool call
            -> Tool / CodeExecutor：执行外部动作
       <- Event stream：把进度与结果交回 Runner
  -> SessionService：持久化 Session、Event、State、Summary

旁路服务：MemoryService / ArtifactService / EvolutionService
边界适配：AG-UI / A2A / OpenAI-compatible server

这张形状图表达的是 owner，不是“所有调用都只有一条直线”。关键结论是： Runner 驱动 Agent，Agent 才驱动 Model；Event 是返回路径上的数据载体，Session 是被服务管理的运行记录。

2.1 Runner：谁把一个请求变成一次可管理的 run

Runner 站在应用入口和 Agent 之间。它先按 app、user、session 找到或创建会话，再选择本次要运行的 Agent， 最后建立 Invocation，把当前消息和可选服务交给 Agent。Agent 返回事件流后，Runner 继续负责取消、持久化、插件回调与对外转发。 因此 Runner 拥有的是一次 run 的生命周期，不是模型推理本身。源码可以从 Run 和 newRunInvocation 开始读。

2.2 Agent：谁决定这一轮采用哪种执行方式

agent.Agent 的核心契约是 Run 返回事件 channel，外加可用 tools、描述信息和 sub-agents。 这意味着 Agent 是框架统一的可执行单元，但它不等于“一个 LLM 循环”。 LLMAgent 会调用模型和工具；GraphAgent 会执行状态图；Chain、Parallel、Cycle 等实现则组合其他 Agent。 Runner 只依赖同一个 Agent interface， 不需要把每种执行策略写进自己。

2.3 Model：谁把模型供应商差异收束成生成接口

model.Model 的公开职责很窄：接收 model.Request，流式返回 model.Response，并报告模型信息。 OpenAI、Anthropic、Gemini 等 adapter 可以有不同 wire shape，但 Agent flow 面向同一 Model interface。 LLMAgent 在运行开始时把选中的模型放进 Invocation，随后 llmflow 才真正调用 GenerateContent。Model 不负责会话落盘、文件版本或用户长期记忆。

2.4 服务和组件为什么不能继续与三者并排

Session、Memory 和 Artifact 都有明确的数据与 service contract：Session 保存当前会话的 Events、State 与 Summaries， session.Service 负责创建、读取和追加；MemoryService 管跨会话事实；ArtifactService 管按 session 和文件名版本化的产物。 Tool 与 CodeExecutor 则是 Agent 可以调用的能力接口。它们很重要，但它们回答的是“状态存哪”“动作怎么做”， 不是“谁驱动这一轮”。

Event 也应放回正确位置：它包着模型 response、调用身份、状态增量和执行元数据，由 Agent 产生、Runner 处理， 再由 SessionService 持久化或由协议层翻译。把 Event 叫成与 Runner、Agent、Model 平级的角色，会掩盖这条流向。 对应结构见 Session、 session.Service 和 Event。

三、沿一次请求看主干怎样调用组件

  1. 网页通过 AG-UI 发来问题；A2A 和 OpenAI-compatible 请求虽然 wire contract 不同，也会先被 adapter 翻成 Runner 能接收的输入。
  2. Runner 用 app、user、session 标识调用 SessionService；命中就恢复 Session，未命中就创建。
  3. Runner 选择 Agent，建立 Invocation，并把 Session、当前消息、MemoryService、ArtifactService 与插件上下文挂进去。
  4. Runner 调 Agent.Run。若选中 LLMAgent，它会选择 Model、运行 request processors，组装模型可见历史、工具声明和生成配置。
  5. Agent flow 调 Model.GenerateContent。Model 返回文本或 tool call；Model 到这里就完成了自己的职责。
  6. 若出现 tool call，LLMAgent 的 flow 调 Tool；代码执行交给 CodeExecutor，生成文件时可以通过 workspace/artifact 工具写入 ArtifactService，然后结果回到下一次模型调用。
  7. 模型片段、tool call、tool result、错误和状态增量被包装成 Event。Runner 一边把 Event 发给调用方，一边通过 SessionService 追加到 Session。
  8. run 完成后，summary、auto memory 和 evolution 可以进入各自后台路径；下一轮再由 processor 把 summary、近期事件和必要 memory 组装成新的模型请求。
Server adapter
  -> Runner.Run(user, session, message)
       -> session.Service.GetSession / CreateSession
       -> Invocation{Agent, Session, services}
       -> Agent.Run
            LLMAgent -> request processors -> model.Model.GenerateContent
                     -> Tool / CodeExecutor
                     <- event.Event stream
       -> session.Service.AppendEvent
  <- 对外 event channel

这是 shape-level 路径，不是逐行复制源码。源码中的关键交接点是 Runner 调 Agent.Run， LLMAgent 再进入 LLM flow， Event 回到 Runner 后由 processSingleAgentEvent 判断持久化与转发。

用户第二天回来时，主干没有变：Runner 重新读取同一 Session，再启动 Agent。变化的是 Agent 交给 Model 的请求投影： 旧事件可以被 summary 压成短上下文，稳定事实可以从 memory 进入，必要时再用 session_load 找回原始证据。 顶部图片讲的正是这条“下一轮模型视图”支线。

仓库 README 把项目定位为 production agent systems 的 Go framework，而不是 memory library。 先学会 Runner → Agent → Model 的调用方向，再用下面这张表压缩 package 分工，才不会把功能清单误当成架构。 项目范围可对照 README feature map。

五、三层主干怎样扩展成完整框架

接下来不平均介绍 package，而是按主干位置看几条会改变应用写法的路径： GraphAgent 扩展 Agent 的执行策略；Skill 与 CodeExecutor 扩展 Agent 的能力面，ArtifactService 接住文件结果； Evolution 挂在 run 完成后的学习支路；AG-UI、A2A 和 OpenAI-compatible server 则站在 Runner 之前翻译外部协议。 这样读，功能再多也不会失去调用方向。

5.1 GraphAgent：流程图先落成状态机，再回到 Agent 接口

先想一个最朴素的做法：让模型在 system prompt 里“按 A、B、C 步执行，必要时并行，最后汇总”。这个做法在 demo 里可行， 但上线后会碰到几个硬问题：条件分支谁保证只走该走的路？并行分支什么时候算结束？中断之后如何恢复？ 工具节点、LLM 节点、子 agent 节点的事件怎样回到同一条 session 里？

tRPC-Agent-Go 的做法是把这部分控制权从 prompt 里拿出来。StateGraph 用 AddNode 包装普通函数节点并创建触发 channel；AddLLMNode、AddToolsNode、 AddAgentNode 把模型、工具和子 agent 也变成图节点；AddEdge 建普通边， AddJoinEdge 建等待多个前驱的 barrier，AddConditionalEdges 和 AddMultiConditionalEdges 建单路或多路条件分发，最后 Compile 做图结构校验。 这部分源码集中在 节点注册 和 边、join、条件路由、compile。

产品问题 runtime 动作 保护的不变量 源码入口
业务想要一个可复现的多步流程。 StateGraph 把节点、边、条件分支和 join 编译成可执行图。 流程结构由 Go 代码验证，不靠模型临场遵守提示词。 state_graph.go
应用仍希望像普通 agent 一样调用这张图。 New 把 StateGraph、channel buffer、并发、checkpoint saver 和 execution engine 交给 executor。 Graph 不变成另一套入口；它仍实现统一的 agent.Agent 运行语义。 graphagent.New、NewExecutor
一轮请求要带着 session 历史、summary、filter、父 agent 信息进入图。 GraphAgent.Run 创建初始 state；createInitialState 复用 content processor，把消息、summary、分支和历史过滤接进来。 图内节点看到的上下文，和普通 LLMAgent 的模型可见上下文保持同一套历史规则。 GraphAgent.Run、createInitialState
图执行要支持并发、checkpoint、resume、barrier 事件和错误收束。 Executor.Execute 为每次运行创建 ExecutionContext，过滤完成 / barrier 事件，准备 checkpoint 和 pending writes，再进入 DAG 或 BSP 执行循环。 executor 可以被重复调用；每次运行的可变状态不会泄漏到下一次运行。 Execute、executeGraph

所以 GraphAgent 不是“多一种 agent 写法”。它真正解决的是流程所有权：模型负责生成内容和工具参数， runtime 负责路由、并发、join、checkpoint、resume 和图事件。这个边界一旦清楚，后面看长上下文就更自然： summary 和 session history 不是图外面的附属品，而是在图初始 state 里被同一套 processor 投影进去。

5.2 Skill + CodeExecutor + Artifact：把能力变成可执行工作区

再看 Skill。如果把它理解成“prompt 片段库”，就会错过框架里最有价值的一层：它把一套能力拆成说明、 可选文档、可选脚本和可执行工作区。模型不需要一开始读完所有材料，也不应该直接拿到任意 shell 权限。

第一层是发现和加载。FSRepository 扫描每个包含 SKILL.md 的目录，建立 skill 元数据； skill_load 校验 skill 是否存在，然后把“已加载 skill、可用 docs、选中的 docs”写成 session state delta。 它的重点不是把所有说明一次性塞进 prompt，而是让模型按需打开能力说明。源码在 FSRepository.Refresh 和 skill_load。

第二层是工具面组合。LLMAgent 会先收集用户传入的 tools、toolsets、knowledge、时间工具等， 再根据 skills 和 executor 判断是否需要 workspace registry，并把 workspace_exec 和 skill tools 接到同一个工具面。 skill profile 也会影响暴露范围：knowledge-only 只给加载和文档选择；完整执行路径才会加上 skill_run、 skill_exec、skill_stdin、skill_poll、skill_kill。 对应源码在 tool surface 构建、 skill profiles 和 appendSkillToolsWithRepoAndFlags。

一步运行 runtime 在做什么 为什么不是 prompt 拼接
模型决定需要某个 skill。 skill_load 记录加载状态和可选文档，而不是执行脚本。 能力说明可以渐进展开，session 里也能看到“加载过什么”。
模型要真正运行 skill。 skill_run 可要求先 load，再应用 artifact 保存覆盖，准备 workspace，执行程序，收集输出和 manifests。 执行入口有状态、参数、输出文件和 artifact 引用，不是自然语言里的一段建议。
脚本需要一个可写目录。 stageSkill 创建可写工作副本；命令策略用 allow / deny 和 CleanEnv 控制执行环境。 runtime 能区分 skill 源文件、工作副本和进程环境，避免把仓库目录当临时目录乱写。
运行产生报告、图片或中间文件。 workspace_save_artifact 把已有 workspace 文件保存成 artifact，返回 artifact:// 引用，并在 state delta 里记录。 大文件不需要内联进模型消息；后续 UI、会话或工具可以按引用取回。

这条链路里，CodeExecutor 和 Artifact 的分工也就清楚了。CodeExecutor 定义“怎样执行代码块”；workspace tools 负责把工作目录、加载后的 skills 和执行引擎接起来；artifact service 负责把文件变成有 app/user/session 归属的持久产物。具体实现可以从 skill_run 的执行入口、 stageSkill、 命令策略、 WithLoadedSkills、 workspace_exec 的服务依赖 和 workspace_save_artifact 串起来读。

5.3 Evolution Service：Skill 不只会被加载，也会被后台学习出来

有了 Skill 工作区以后，下一个问题自然出现：新 skill 从哪里来？最简单但危险的做法，是让前台 agent 在完成任务时顺手改 SKILL.md。这样会把用户请求、文件写入、长期事实、一次性输出和库维护混在一起：模型可能把某个用户事实写成通用技能， 也可能为了当前任务写出不可复用的流程。

tRPC-Agent-Go 把这件事拆成后台学习管线。runner.WithEvolutionService 把 service 挂到 Runner； runner completion 之后会调用 enqueueEvolutionLearningJob，用 context.WithoutCancel 把当前 session 送进 worker。worker 读取 evolution:last_review_at 之后的增量，扫描消息、tool calls、用户纠正和错误恢复信号， 再交给 ReviewPolicy 判断是否值得 review。触发条件默认是至少 4 次 tool call、出现用户纠正，或者工具错误后被 assistant 恢复。 源码在 enqueueEvolutionLearningJob、 processJob、 scanDelta 和 DefaultReviewPolicy。

学习阶段 runtime 做什么 保护的不变量 源码入口
完成后排队 Runner 在 completion 后排 auto memory，也排 evolution learning job；请求上下文被 detach，worker 自己管理超时。 前台响应不被 review 阻塞，后台学习不会因为请求结束而立刻取消。 completion hook、worker.Enqueue
构造 review 输入 worker 只看上次 review 之后的 session delta，并给 reviewer 当前 skill library 的名称、描述和 body excerpt。 学习不是重读无限历史，也不是忽略已有技能导致重复造轮子。 ReviewInput、buildUserPrompt
Reviewer 决策 LLM reviewer 只能返回 skip_reason、skills、updates、deletions 的 JSON。 Evolution 只拥有 skill library；用户事实和 episode 留给 memory 管线。 review prompt、ReviewDecision / SkillSpec
发布或拦截 raw decision 先经过 library-aware reconciler；如果配置了 gate，就写候选 revision、跑 spec/safety/effectiveness/human gate，再发布到 managed skills。 不会让一次性、重复、危险或未经批准的技能直接变成下次可用能力。 reconcileWithLibrary、processRevision、runGates

发布后的结果仍然回到 Skill 主线：filePublisher 把 skill 写成 managed 目录下的 SKILL.md，applyDecision 在发生变更后刷新 repository，下一轮 LLMAgent 就能通过 skill_load 或 overview 看到新能力。如果启用了 revision 管线，Revision 还会带着 pending、active、rejected、pending_eval、pending_approval 等状态，ApprovalService 可以把 pending approval 的 revision 交给外部人审后再 promote。 这部分源码在 Publisher、 applyDecision、 Revision lifecycle 和 ApprovalService。

这样看，自进化不是“模型改自己的 prompt”，而是完成任务后的技能库维护管线。 它读 session delta，写 managed skills；它可以借 evaluator outcome 做 failure-aware learning，但不会替 memory 写事实。 这也解释了为什么它应该接在 Skill 之后讲：没有 Skill 的加载、执行、隔离和刷新，自进化产物就没有自然的落点。

5.4 AG-UI：前端协议不是壳子，它重新定义输入、运行和事件翻译边界

前端接 agent 时，最容易低估协议层。一个文本流接口只要把 assistant delta 往外推就行； 但 AG-UI 还要处理用户消息、tool result 消息、多模态内容、外部工具、运行取消、runtime state、graph interrupt、 artifact、reasoning、tool call lifecycle 和最终完成事件。这里的 server adapter 不是示例 glue code，而是运行时边界。

server/agui.New 先把底层 runner.Runner 包成 service 和 HTTP handler， 配上 path、cancel、snapshot 等选项。真正进入运行时之前，adapter 使用 AG-UI SDK 的 RunAgentInput； inputMessagesFromRunAgentInput 要求最后一条输入是 user 或 tool message，并且会把连续的 trailing tool results 归成这次 run 的输入结果。源码入口在 server/agui.New、 service wrapper、 RunAgentInput alias 和 输入消息解析。

接着 Runner.Run 解析 userID、run options、外部 tools、appName、runtimeState， 重写 tool result messages，注册 execution 以支持取消，并创建 translator。真正跑起来时，它会先发 RunStarted，把输入里的 tool result 也翻译成前端可见事件；如果图处在 interrupt resume 场景， 还会补一段 resume event，然后才调用底层 runner，把内部 agent event 逐个交给 handleAgentEvent。 对应源码在 Runner.Run 和 runner.run。

translator 是 AG-UI 这层最值得看的对象。它保存一次 run 内的 seen IDs、tool call deltas、graph lifecycle flags、 reasoning stream 和 artifact 状态，然后把内部事件翻译成 AG-UI 的 graph、text、reasoning、tool call、tool result、 artifact、queued user message、RunFinished 等事件。源码在 Translator state、 事件翻译主线 和 source metadata finalize。

这就是为什么协议层不能只看成 HTTP 外壳：UI 看到的 run id、tool call id、graph 活动状态、artifact 引用、 外部 tool result 和最终完成信号，都不是模型文本天然携带的东西。AG-UI adapter 把这些运行时事件翻译成前端能稳定消费的协议事件。

5.5 A2A 与 OpenAI-compatible：同一个 Runner，不同的 continuity contract

AG-UI 只是 server plane 的一种出口。A2A 和 OpenAI-compatible 也会进入同一个 Runner，但“怎样认出同一次连续工作”、 “历史由谁携带”、“事件怎样出站”并不相同。把三者放在一起看，才能避免把协议 adapter 理解成换一个 URL。

协议面 连续性怎样进入 Runner 结果怎样离开 Runner 最重要的边界
AG-UI RunAgentInput 带 user/tool 尾消息、runtime state、外部工具和 run 语义。 翻译成 graph、text、reasoning、tool、artifact、cancel 和 finish 等富事件。 连续性围绕前端 run 和可恢复 UI state。
A2A AgentCard 描述能力，message processor 把 ContextID 映射为 session，并把 message metadata 带入 runtime state。 通过 task manager 输出 submitted/status、artifact update、completed 或结构化失败。 连续性围绕跨 agent 的 context 与 task lifecycle。
OpenAI-compatible /v1/chat/completions 取最后一条为当前消息，把此前 messages 作为 WithMessages，用 X-Session-ID 延续 session。 非流式聚合内部 events；流式输出 Chat Completions SSE chunks，最后发送 [DONE]。 这是 Chat Completions 兼容层，不是 Responses API 的 item/event 模型。

A2A 入口可以接收现成 Runner，也可以从 Agent 创建 Runner；如果直接传 Runner，还必须提供 AgentCard。 buildProcessor 组装 A2A message 到 agent message、内部 event 到 A2A result 的双向 converter。 真正处理消息时，processor 从 ContextID 建 session continuity，把 metadata 复制为 runtime state， 然后把 Runner event 变成 task status、artifact 和 completion。对应源码在 a2a.New、 buildProcessor、 message 与 streaming task setup 和 task status / artifact / completion 翻译。

OpenAI-compatible 层则刻意收窄成 /v1/chat/completions：server 可以复用外部 Runner，或为 Agent 创建并拥有一个 Runner； request converter 把最后一条消息作为当前输入，把之前的消息通过 agent.WithMessages 带入。 非流式请求也会收齐所有内部 events 再聚合；流式请求把 event 转成 SSE chunk 并以 [DONE] 收尾。 这个快照里，temperature、max_tokens 等请求级 generation 参数还不会下传，应该在创建 Agent 时配置。 源码在 server 与路由、 非流式 history / session / event aggregation 和 流式 SSE path。

所以“共用 Runner”只说明运行核心统一，不表示 wire semantics 相同。前端续跑、跨 agent task、OpenAI SDK 兼容 分别需要不同的 identity、history 和 event contract；应用迁移协议时，不能只替换 endpoint。

先有 runtime 地图，再看 memory 才不会偏。 Graph、Skill 工作区、Evolution 和 AG-UI 都在说明同一个边界：模型不是 runtime。 summary 和 memory 不是孤立功能，而是 Runner 持久化事件、processor 组装模型请求、tool surface 暴露召回入口、 server 层持续承接会话之后，才自然冒出来的长上下文 owner。

六、长上下文重点：先分清三本账

很多 agent 框架都会暴露 memory 这个词，但这个词太宽了。tRPC-Agent-Go 的源码更像把它拆成三本账： 原始 session events、session summary、长期 memory。读懂这三本账，后面的函数名就不会散。

  • Session events 是原始工作日志：用户说过什么、查了哪份日志、工具返回什么，都按时间保留。
  • Summary 是当前工单的交接摘要：旧记录太长时，把已经发生的部分压成短说明，让同一会话继续跑。
  • Memory 是跨工单的客户档案：例如用户长期使用的技术栈或稳定偏好，未来新会话也可以复用。

仍以客服为例：昨天完整的报错行留在 events；“已排除网络问题，正在检查证书”可以进入 summary； “该用户的生产环境使用 Go”可以成为 memory。若今天必须核对昨天那一行原始错误，session_load 再从 events 取回证据。Evolution 则把“遇到这类错误先检查证书”沉淀成操作方法，因此它不是第四本记忆账。 

Session ledger
  Session{Events, Summaries[filterKey]*Summary}
  Summary{Summary, Topics, Boundary{FilterKey, CutoffAt, LastEventID}}

Memory ledger
  Entry{ID, AppName, UserID, Memory, CreatedAt, UpdatedAt}
  Memory{Memory, Topics, Kind(fact|episode), EventTime, Participants}

Evolution path
  LearningJob{Session, Outcome?, Scope}
  ReviewDecision{Skills, Updates, Deletions}

Recall path
  session_search / session_load
  current visible history + current_hidden history + other searchable scopes

这四行能防止一个常见误读：session summary、memory 和 evolution 都会读会话，但它们不是同一个东西。 summary 写回 session summary；memory 写 app/user 维度的事实或 episode；evolution 写 managed skill library； session_load 则回到原始事件账本找被 summary 隐掉的证据。

账本 它保存什么 什么时候进模型 第一眼源码
Session events 一次会话里的用户消息、assistant 事件、tool 结果、状态变化和轨迹。 默认按事件顺序进入上下文；当 summary 有边界时，只取边界之后的增量。 Session 字段
Session summary 对当前 session 某个 filter key 下旧事件的压缩文本，以及压缩到哪里的边界。 由 content processor 注入为模型可见上下文，同时只追加 summary 边界之后的消息。 Summaries、appendSessionMessages
Memory 跨 session 的事实和 episode，带 app、user、kind、时间、topic、metadata。 可以通过 preload 放进上下文，也可以由 memory_search / memory_load 工具按需读取。 memory.Service、Memory / Entry

这张表的关键不是“有三个结构体”。关键是：summary 不是长期记忆，memory 也不是聊天摘要。 summary 的任务是让当前会话继续跑；memory 的任务是让未来会话还能拿到稳定事实。

这里顺手把 evolution 的位置摆正：它也读 session delta，但它不是第四本“记忆账”。源码里的 ReviewDecision 注释明确说 evolution 不抽取 durable facts，fact-style memory 属于 memory.Service 和 auto-memory extractor；evolution 只拥有 skill library。也就是说，同一段会话可以同时被 summary 压短、被 memory 抽事实、 被 evolution 抽流程，但三者写入的目标完全不同。证据在 ReviewDecision boundary 和 worker scope comment。

七、Runner 负责把长上下文账本接到运行主线

tRPC-Agent-Go 的 Runner 负责模型调用前后的运行生命周期，但它不直接调用模型。它先拿到或创建 Session， 把当前消息、Agent、SessionService、MemoryService、ArtifactService、插件和运行选项挂到 Invocation 上，再调用 Agent.Run。如果这次运行由 LLMAgent 执行，LLM flow 才会准备请求并调用 Invocation.Model.GenerateContent。这个边界很重要：长上下文账本由 Runner 接入，模型请求由 Agent 层组装和发出。证据在 Run 、 newRunInvocation 和 provider call。

真正有意思的是事件落盘之后发生什么。handleEventPersistence 过滤 partial、无效事件、tool result 等特殊情况， 把有效事件写进 session，然后按事件的 FilterKey 触发 summary job；runner 完成事件之后，又会触发 auto memory 抽取， 也会在配置了 evolution service 时排一个 evolution learning job。 这些入口分别在 handleEventPersistence、 runner completion 和 enqueueEvolutionLearningJob。

这里的设计味道是“运行时自动收账”。 应用不需要在每一轮手写“如果上下文太长就总结一下，再顺便抽取长期记忆，最后复盘能不能沉淀技能”。runner 把事件持久化、 summary 调度、auto memory 调度和 evolution 学习入口都接在运行主线后面，但每条后台管线写入不同 owner。

八、summary：压当前 session，不删原始账

summary 的第一步不是“调用模型总结全文”，而是先判断这一轮是不是该总结。summary 包暴露的接口是 ShouldSummarize 和 Summarize，还支持带 invocation context 的版本。 接口定义在 SessionSummarizer。

1. 先过触发门槛

summary 的门槛可以按事件数、token 数、时间、上下文窗口比例组合。WithTokenThreshold、 WithEventThreshold、WithTimeThreshold 是静态阈值； WithContextThreshold 会结合 invocation context、当前模型和上下文窗口动态判断。 证据在 threshold options 和 WithContextThreshold。

如果配置了异步 worker，summary job 会被放进 hash 分片队列；队列满、worker 不存在或配置要求 fallback 时，再走同步总结。 EnqueueJob 会 detach context、按 session/filter 路由，并保留 cascade full-session summary 的兜底路径。 证据在 AsyncSummaryWorker.EnqueueJob。

2. 只总结边界之后的增量

进入真正总结时，内部逻辑会先拿锁，避免同一个 session/filter 的总结并发重复。然后它读取上一次 summary， 计算 boundary 之后的 delta，把旧 summary 作为上下文前缀拼回去，再构造临时 session 给 summarizer 判断。 这段在 SummarizeSession、 buildSummaryInput 和 summary lock。

summarizer 本身也不是只拼文本内容。它会过滤要总结的事件、跳过最近几条、把用户/assistant 文本、tool call、tool result 都抽成对话文本，再调用模型生成 summary。关键代码在 Summarize、 filterEventsForSummary 和 extractConversationText。

3. summary 进入模型视图，而不是替代 session

生成出来的 summary 会写回 session summary store，并记录边界。下一轮组装模型请求时， content processor 会先取 summary 文本和 cutoff，再把 summary 注入系统消息或用户消息，最后只追加 cutoff 之后的 session messages。 源码在 writeSummary、 appendSummaryContext 和 sessionMessagesAfterCutoff。

这就是“summary 压会话”的准确含义：它压的是模型可见上下文，不是删除原始事件。原始 events 仍然在 session 里， 后面 session_search 和 session_load 还能回头找。

4. cache-safe fork 解决的不是语义，而是 provider 请求形状

这里有个很工程化的细节。普通总结可以把抽出的对话文本放进一个新的 summary prompt 里；但当 provider 有 prompt cache、 reasoning、工具定义或特殊 request shape 时，完全新开的总结请求可能破坏缓存形状。WithCacheSafeForking 会在有 parent model request 时克隆父请求，再追加一个“压缩当前上下文”的用户消息；没有父请求时才退回 standalone prompt。 证据在 WithCacheSafeForking 和 cache-safe fork request clone。

pre-LLM context compaction 也沿着这个思想走：在真正调用模型前判断上下文是否需要压缩，必要时同步创建 summary， 把 parent request 附给 summary context，然后重建模型请求。证据在 maybeCompactContextBeforeLLM 和 runContextCompaction。

九、memory：存长期事实，不替代 summary

memory 的接口更像一个长期资料库。memory.Service 明确暴露 Add、Update、Delete、Clear、Read、Search、Tools、 EnqueueAutoMemoryJob 和 Close。它保存的是 KindFact 或 KindEpisode 的条目，而不是“本轮上下文摘要”。 源码在 Service 和 Kind / Entry。

1. 工具入口是显式的

框架内置的 memory 工具有六个名字：memory_add、memory_update、memory_delete、 memory_clear、memory_search、memory_load。工具实现会从 invocation context 拿 memory service、 app name 和 user id，再执行对应操作。search/load 返回的是结构化条目，而不是把全部 memory 粘进 prompt。 源码在 tool names、 memory_search / memory_load 和 context lookup。

search 的默认行为也透露出它的定位：它会构造 SearchOptions，默认开启 deduplicate 和 hybrid search， 支持 kind、时间范围、最大条数、相似度阈值、排序和 RRF。证据在 SearchOptions 和 buildSearchOptions。

2. auto memory 是“跑完后抽取”，不是“每条消息立刻写事实”

runner 完成一次运行后会调用 enqueueAutoMemoryJob；memory service 如果配置了 extractor， 就把当前 session 交给 auto memory worker。源码在 enqueueAutoMemoryJob 和 NewMemoryService。

worker 不会盲目把整段历史扔给模型。EnqueueJob 先读取上次抽取位置，扫描 delta， 只保留用户和 assistant 文本，排除 tool messages 和 tool calls；再根据阈值检查是否值得抽取。 证据在 AutoMemoryWorker.EnqueueJob 和 scanDeltaSince。

真正抽取时，它先用用户消息构造查询，搜索已有相关 memories；再把“现有记忆 + 新对话”交给 extractor， 让模型产出 add/update/delete/clear 操作；最后通过 reconcile 和 enabled tool gate 执行。源码在 createAutoMemory、 Extract 和 executeOperation。

3. preload 是给模型一小块长期背景

如果开启 preload memory，content processor 会先构造 memory prompt，把选中的长期记忆以规则化格式放进上下文。 它不是把所有 memory 一次性塞满，而是提供“可用背景”和“如何使用这些记忆”的提示。 证据在 WithPreloadMemory 和 preload memory prompt。

memory 的边界很重要。 它负责“以后也可能用到的事实和 episode”，不负责把当前 session 的每个旧事件压缩给下一轮模型。 当前 session 的压缩是 summary 的事；长期事实的沉淀才是 memory 的事。

十、session_search / session_load 是隐藏历史的回收通道

一旦 summary 生效，模型主上下文里只保留 summary + cutoff 之后的增量。那旧的原始事件是不是就找不到了？ 不是。tRPC-Agent-Go 还有 session recall tools。session_search 可以在当前可见、当前隐藏、其他 session 等 scope 里查找，current_hidden 会结合 summary boundary，只搜当前 session 里被 summary 隐掉的历史。 源码在 searchCurrentHidden。

session_load 则负责把命中的 anchor 周围一段原始事件窗口加载回来。窗口逻辑按事件顺序切片， 不是让模型凭 summary 猜。源码在 resolveLoadAnchorEventID 和 EventWindowFromOrderedEvents。

这样 summary 的代价就被控制住了：主上下文可以变短，但原始证据没有丢；模型需要细节时，可以通过 recall tool 回到原账本。

十一、放回 Agent 框架路线里看

这一篇和 Eino 的关系很近，但关注点不同。Eino 先回答 Go 里怎样把 component、stream、interrupt、agent loop 放进可组合执行图；tRPC-Agent-Go 则先建立 Runner → Agent → Model 的服务端执行主干，再把 GraphAgent 放进 Agent 的执行策略， 把 tools、Skills、CodeExecutor 放进能力层，把 Session、Memory、Artifact 放进服务层，并在运行前后接上协议 adapter 与 Evolution Service。 本文后半篇重点看的，是这套 runtime 里最容易被误读的 summary / memory / evolution / hidden-history recall。

容易误解的说法 更准确的读法
memory 就是把聊天记录总结一下。 summary 压当前 session；memory 存跨 session 的事实和 episode。
有 summary 就可以删旧事件。 summary 只改变模型主上下文；旧事件仍服务于 session_search / session_load。
auto memory 每句话都写入长期记忆。 runner 完成后触发 worker，扫描 delta、过阈值、搜索已有记忆、再抽取操作。
self-evolution 就是模型自己改 prompt 或记住用户事实。 evolution 只维护 managed skill library：review session delta，生成 skill create/update/delete，经过 reconciler 和 gate 后发布。
长上下文模型出来后 summary 不重要。 summary 还承担成本、缓存形状、工具 transcript 和恢复边界治理。

所以这篇的结论要分两层：整体上，tRPC-Agent-Go 是 Go agent 的服务端 runtime；细节上，它的长上下文 owner 不是一个 memory 开关，而是两本账和一个回收通道。 Runner 管理一次运行并注入服务，Agent 决定怎样执行并调用 Model；Graph、Skills、CodeExecutor 扩展 Agent 的执行与行动方式， Session、Memory、Artifact 分别保存会话账本、跨会话事实和版本化文件，协议 adapter 负责对外翻译。 Evolution 把可复用流程沉淀回 managed skills；summary 让当前 Session 继续跑，memory 让长期事实留下来， session_load 让被 summary 隐掉的原始历史还能被找回。
