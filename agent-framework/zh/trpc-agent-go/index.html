tRPC-Agent-Go 把 Go agent 做成服务端 runtime

Eino 那篇讲 Go agent 怎么被收束进可组合执行图。tRPC-Agent-Go 继续往服务端 runtime 走： Runner 管 session 和运行边界，GraphAgent 管确定性流程，tools / skills / codeexecutor / artifact 管副作用， AG-UI、A2A 和 OpenAI-compatible server 管对外协议。后半篇再重点拆 Rememorio 推进最集中的 summary 与 memory。

主题：tRPC-Agent-Go 框架：Runner / Graph / Skill / Server 重点：summary / memory / session_load

如果只盯着 memory 和 summary，会误会 tRPC-Agent-Go 只是给 Go agent 加了一组长上下文插件。 其实它更像把 agent 产品上线后会遇到的几类 owner 都摆出来：谁负责一次运行，谁负责确定性流程，谁负责工具和代码执行， 谁负责文件产物，谁负责前端协议，谁负责长期状态。

上面的图先画出后半篇重点：长上下文。先想一个真实产品场景：一个企业客服 agent 连续几天帮同一个用户排查问题。 第一天它看过日志，第二天它调用过内部工单工具，第三天用户说“还是昨天那个错误”。这时框架既要能服务化运行， 也要能把旧会话压短、把长期事实留下来、在需要时召回原始证据。

阅读契约。 这一篇先把框架 owner 讲清楚，再进入 Rememorio 推进最集中的长上下文线。不是堆模块名， 而是问：一个 Go agent 产品上线以后，Runner、Graph、tools、skills、codeexecutor、artifact、server 和 memory 分别替应用承担了什么。

证据边界。 源码链接固定到公开快照 d3b50fd90d60b4ece8a78e89cf890a4f06d78235。 文中“owner”“账本”“投影”是工程归纳；具体行为以公开源码中的 runner、agent、graph、tool、skill、artifact、server、 summary、memory 和 processor 为准。

一、先看整体：它把 Go agent 拆成哪些 owner

仓库 README 对自己的定位不是“memory library”，而是“building production agent systems”的 Go framework： 它把 LLM agents、graph workflows、tool calling、session/memory state、knowledge retrieval、self-evolution、evaluation、 OpenTelemetry，以及 A2A、AG-UI、MCP 集成放在同一套 Go-native stack 里。对应的源码结构也比较清楚： README feature map 和 package table 都在描述一个服务端 agent runtime。

Runtime owner 它替应用接住什么 小白可以先这样理解 第一眼源码
Runner / Invocation 一次请求的 app、user、session、message、agent、memory service、artifact service、plugins 和 run options。 不是直接调模型，而是先搭好“这一轮运行的上下文”。 runner fields、newRunInvocation
Agent family LLMAgent 包模型、工具、planner、sub-agents；Chain/Parallel/Cycle 把多个 agent 组合成不同执行形态。 一个 agent 可以是模型循环，也可以是一组子 agent 的编排器。 Agent interface、LLMAgent、ParallelAgent
GraphAgent / StateGraph 确定性节点、条件路由、多分支并行、join、LLM node、tools node、agent node、checkpoint / interrupt 选项。 把“流程图”从 prompt 里拿出来，变成 Go 代码里的可验证执行图。 StateGraph、GraphAgent
Tool / Skill / CodeExecutor / Artifact 把 Go 函数、MCP tools、SKILL.md 工作流、代码执行和版本化文件产物接进同一套工具面。 模型不是只会说话，它可以按受控入口调用外部能力，并把结果保存成可追踪产物。 tool、skill.Repository、artifact.Service
Server plane 把同一个 Runner 暴露给 AG-UI 前端、A2A agent 互操作和 OpenAI-compatible chat completions。 协议出口不是示例代码，而是 runtime 的一层 adapter。 server/agui、server/a2a、server/openai

这张表的读法是：tRPC-Agent-Go 并不要求业务把所有复杂度都塞进一个“超级 Agent”类里。 它把服务端 agent 会遇到的问题拆成不同 owner。后面的长上下文治理，正是 Runner、Session、Summary、Memory、Processor 这些 owner 合作出来的结果。

二、Graph、Skill、CodeExecutor、Artifact、AG-UI 分别解决什么

先把几个容易被名字带偏的模块讲白。Graph 不是让模型“想一个计划”，而是用 AddNode、AddEdge、AddConditionalEdges、AddMultiConditionalEdges、Compile 这些 Go API 把流程图变成可执行结构；GraphAgent 再把这张图塞回统一的 agent.Agent 接口。 源码在 AddNode / LLM / tools / agent node、 edges and compile 和 GraphAgent.Run。

Skill 也不是 prompt 片段库。它把一个能力做成包含 SKILL.md 和可选 docs/scripts 的文件夹， 由 FSRepository 扫描、刷新、按名读取；LLMAgent 再按 profile 注册 skill_load、 skill_list_docs、skill_select_docs，以及兼容路径里的 skill_run / skill_exec。 这样模型先加载说明，再按受控执行入口跑命令，而不是把整套脚本都塞进提示词。 证据在 NewFSRepository / Refresh、 skill tool profiles 和 skill_load。

CodeExecutor 和 Artifact 则把“执行代码”和“保存结果文件”分开。前者定义 ExecuteCode 和 code block delimiter，后者定义按 app/user/session/filename 保存、加载、列版本、删除 artifact。 SaveArtifactHelper / LoadArtifactHelper 让代码执行层能通过 context 找到 artifact service， 所以工具生成图片、报告或中间文件时，不必把大文件内联进模型输出。 源码在 CodeExecutor、 LoadArtifactHelper、 SaveArtifactHelper 和 artifact.Service。

协议层也值得讲。server/agui 会把 Runner 包成 AG-UI runner，解析前端 run input，解析 app/user/state/run options， 再用 translator 把内部事件翻译成 AG-UI 事件；server/a2a 可以从 agent 信息生成 AgentCard 并构造 A2A message processor； server/openai 则把 Runner 接成 /v1/chat/completions 风格的 HTTP handler。 这意味着同一套 agent runtime 可以服务前端、其他 agent 和 OpenAI-compatible 客户端。 源码在 AG-UI runner、 AG-UI run input、 A2A processor 和 OpenAI server。

先有 runtime 地图，再看 memory 才不会偏。 summary 和 memory 不是孤立功能，而是 Runner 持久化事件、processor 组装模型请求、tool surface 暴露召回入口、 server 层持续承接会话之后，才自然冒出来的长上下文 owner。

三、长上下文重点：先分清三本账

很多 agent 框架都会暴露 memory 这个词，但这个词太宽了。tRPC-Agent-Go 的源码更像把它拆成三本账： 原始 session events、session summary、长期 memory。读懂这三本账，后面的函数名就不会散。

账本 它保存什么 什么时候进模型 第一眼源码
Session events 一次会话里的用户消息、assistant 事件、tool 结果、状态变化和轨迹。 默认按事件顺序进入上下文；当 summary 有边界时，只取边界之后的增量。 Session 字段
Session summary 对当前 session 某个 filter key 下旧事件的压缩文本，以及压缩到哪里的边界。 由 content processor 注入为模型可见上下文，同时只追加 summary 边界之后的消息。 Summaries、appendSessionMessages
Memory 跨 session 的事实和 episode，带 app、user、kind、时间、topic、metadata。 可以通过 preload 放进上下文，也可以由 memory_search / memory_load 工具按需读取。 memory.Service、Memory / Entry

这张表的关键不是“有三个结构体”。关键是：summary 不是长期记忆，memory 也不是聊天摘要。 summary 的任务是让当前会话继续跑；memory 的任务是让未来会话还能拿到稳定事实。

四、Runner 负责把长上下文账本接到运行主线

tRPC-Agent-Go 的 runner 不只是调用 agent 的外壳。它在每次运行时拿到或创建 session，把当前用户消息、agent、session service、 memory service 和插件上下文挂到 invocation 上，然后让 agent 运行。证据在 Run 和 newRunInvocation。

真正有意思的是事件落盘之后发生什么。handleEventPersistence 过滤 partial、无效事件、tool result 等特殊情况， 把有效事件写进 session，然后按事件的 FilterKey 触发 summary job；runner 完成事件之后，又会触发 auto memory 抽取。 这两处分别在 handleEventPersistence 和 runner completion。

这里的设计味道是“运行时自动收账”。 应用不需要在每一轮手写“如果上下文太长就总结一下，再顺便抽取长期记忆”。runner 把事件持久化、summary 调度和 auto memory 调度都接在运行主线后面。

五、summary：压当前 session，不删原始账

summary 的第一步不是“调用模型总结全文”，而是先判断这一轮是不是该总结。summary 包暴露的接口是 ShouldSummarize 和 Summarize，还支持带 invocation context 的版本。 接口定义在 SessionSummarizer。

1. 先过触发门槛

summary 的门槛可以按事件数、token 数、时间、上下文窗口比例组合。WithTokenThreshold、 WithEventThreshold、WithTimeThreshold 是静态阈值； WithContextThreshold 会结合 invocation context、当前模型和上下文窗口动态判断。 证据在 threshold options 和 WithContextThreshold。

如果配置了异步 worker，summary job 会被放进 hash 分片队列；队列满、worker 不存在或配置要求 fallback 时，再走同步总结。 EnqueueJob 会 detach context、按 session/filter 路由，并保留 cascade full-session summary 的兜底路径。 证据在 AsyncSummaryWorker.EnqueueJob。

2. 只总结边界之后的增量

进入真正总结时，内部逻辑会先拿锁，避免同一个 session/filter 的总结并发重复。然后它读取上一次 summary， 计算 boundary 之后的 delta，把旧 summary 作为上下文前缀拼回去，再构造临时 session 给 summarizer 判断。 这段在 SummarizeSession、 buildSummaryInput 和 summary lock。

summarizer 本身也不是只拼文本内容。它会过滤要总结的事件、跳过最近几条、把用户/assistant 文本、tool call、tool result 都抽成对话文本，再调用模型生成 summary。关键代码在 Summarize、 filterEventsForSummary 和 extractConversationText。

3. summary 进入模型视图，而不是替代 session

生成出来的 summary 会写回 session summary store，并记录边界。下一轮组装模型请求时， content processor 会先取 summary 文本和 cutoff，再把 summary 注入系统消息或用户消息，最后只追加 cutoff 之后的 session messages。 源码在 writeSummary、 appendSummaryContext 和 sessionMessagesAfterCutoff。

这就是“summary 压会话”的准确含义：它压的是模型可见上下文，不是删除原始事件。原始 events 仍然在 session 里， 后面 session_search 和 session_load 还能回头找。

4. cache-safe fork 解决的不是语义，而是 provider 请求形状

这里有个很工程化的细节。普通总结可以把抽出的对话文本放进一个新的 summary prompt 里；但当 provider 有 prompt cache、 reasoning、工具定义或特殊 request shape 时，完全新开的总结请求可能破坏缓存形状。WithCacheSafeForking 会在有 parent model request 时克隆父请求，再追加一个“压缩当前上下文”的用户消息；没有父请求时才退回 standalone prompt。 证据在 WithCacheSafeForking 和 cache-safe fork request clone。

pre-LLM context compaction 也沿着这个思想走：在真正调用模型前判断上下文是否需要压缩，必要时同步创建 summary， 把 parent request 附给 summary context，然后重建模型请求。证据在 maybeCompactContextBeforeLLM 和 runContextCompaction。

六、memory：存长期事实，不替代 summary

memory 的接口更像一个长期资料库。memory.Service 明确暴露 Add、Update、Delete、Clear、Read、Search、Tools、 EnqueueAutoMemoryJob 和 Close。它保存的是 KindFact 或 KindEpisode 的条目，而不是“本轮上下文摘要”。 源码在 Service 和 Kind / Entry。

1. 工具入口是显式的

框架内置的 memory 工具有六个名字：memory_add、memory_update、memory_delete、 memory_clear、memory_search、memory_load。工具实现会从 invocation context 拿 memory service、 app name 和 user id，再执行对应操作。search/load 返回的是结构化条目，而不是把全部 memory 粘进 prompt。 源码在 tool names、 memory_search / memory_load 和 context lookup。

search 的默认行为也透露出它的定位：它会构造 SearchOptions，默认开启 deduplicate 和 hybrid search， 支持 kind、时间范围、最大条数、相似度阈值、排序和 RRF。证据在 SearchOptions 和 buildSearchOptions。

2. auto memory 是“跑完后抽取”，不是“每条消息立刻写事实”

runner 完成一次运行后会调用 enqueueAutoMemoryJob；memory service 如果配置了 extractor， 就把当前 session 交给 auto memory worker。源码在 enqueueAutoMemoryJob 和 NewMemoryService。

worker 不会盲目把整段历史扔给模型。EnqueueJob 先读取上次抽取位置，扫描 delta， 只保留用户和 assistant 文本，排除 tool messages 和 tool calls；再根据阈值检查是否值得抽取。 证据在 AutoMemoryWorker.EnqueueJob 和 scanDeltaSince。

真正抽取时，它先用用户消息构造查询，搜索已有相关 memories；再把“现有记忆 + 新对话”交给 extractor， 让模型产出 add/update/delete/clear 操作；最后通过 reconcile 和 enabled tool gate 执行。源码在 createAutoMemory、 Extract 和 executeOperation。

3. preload 是给模型一小块长期背景

如果开启 preload memory，content processor 会先构造 memory prompt，把选中的长期记忆以规则化格式放进上下文。 它不是把所有 memory 一次性塞满，而是提供“可用背景”和“如何使用这些记忆”的提示。 证据在 WithPreloadMemory 和 preload memory prompt。

memory 的边界很重要。 它负责“以后也可能用到的事实和 episode”，不负责把当前 session 的每个旧事件压缩给下一轮模型。 当前 session 的压缩是 summary 的事；长期事实的沉淀才是 memory 的事。

七、session_search / session_load 是隐藏历史的回收通道

一旦 summary 生效，模型主上下文里只保留 summary + cutoff 之后的增量。那旧的原始事件是不是就找不到了？ 不是。tRPC-Agent-Go 还有 session recall tools。session_search 可以在当前可见、当前隐藏、其他 session 等 scope 里查找，current_hidden 会结合 summary boundary，只搜当前 session 里被 summary 隐掉的历史。 源码在 searchCurrentHidden。

session_load 则负责把命中的 anchor 周围一段原始事件窗口加载回来。窗口逻辑按事件顺序切片， 不是让模型凭 summary 猜。源码在 resolveLoadAnchorEventID 和 EventWindowFromOrderedEvents。

这样 summary 的代价就被控制住了：主上下文可以变短，但原始证据没有丢；模型需要细节时，可以通过 recall tool 回到原账本。

八、放回 Agent 框架路线里看

这一篇和 Eino 的关系很近，但关注点不同。Eino 先回答 Go 里怎样把 component、stream、interrupt、agent loop 放进可组合执行图；tRPC-Agent-Go 更进一步，把 Runner、GraphAgent、tool surface、Skills、code executor、artifact store、 AG-UI/A2A/OpenAI server 和长上下文状态都放进一个 Go 服务端 runtime。本文后半篇重点看的，是这个 runtime 里最容易被误读的 summary / memory / hidden-history recall。

容易误解的说法 更准确的读法
memory 就是把聊天记录总结一下。 summary 压当前 session；memory 存跨 session 的事实和 episode。
有 summary 就可以删旧事件。 summary 只改变模型主上下文；旧事件仍服务于 session_search / session_load。
auto memory 每句话都写入长期记忆。 runner 完成后触发 worker，扫描 delta、过阈值、搜索已有记忆、再抽取操作。
长上下文模型出来后 summary 不重要。 summary 还承担成本、缓存形状、工具 transcript 和恢复边界治理。

所以这篇的结论要分两层：整体上，tRPC-Agent-Go 是 Go agent 的服务端 runtime；细节上，它的长上下文 owner 不是一个 memory 开关，而是两本账和一个回收通道。 Runner 让这些 owner 接到运行主线，Graph / Skills / CodeExecutor / Artifact / Server plane 扩展 agent 的生产形态； summary 让当前 session 继续跑，memory 让长期事实留下来，session_load 让被 summary 隐掉的原始历史还能被找回。
