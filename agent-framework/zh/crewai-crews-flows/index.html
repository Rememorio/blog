CrewAI 把 agent 写成团队流程，而不是消息总线

前一篇从 AutoGen 和 Microsoft Agent Framework 看到 message runtime 到 production orchestration 的迁移。 CrewAI 的入口不在消息总线，而在应用开发者熟悉的团队模型：agent 有 role、goal、backstory，task 有 description、 expected output 和 guardrail，crew 决定 process，flow 决定生产控制。

主题：CrewAI 主线：Crew autonomy + Flow control 重点：Agent / Task / Crew / Flow

CrewAI README 的定位非常直接：它是一个从零构建的 Python multi-agent automation framework， 明确独立于 LangChain 或其他 agent framework；同一段把产品分成 CrewAI Crews 和 CrewAI Flows。Crews 优化 autonomy 和 collaborative intelligence，Flows 则是构建和部署 multi-agent systems 的 enterprise and production architecture，强调 granular event-driven control、single LLM calls、 task orchestration，并且原生支持 Crews。 证据在 CrewAI README overview。

README 后面又把这条线说得更清楚：Crews 是带 autonomy 和 agency 的 AI agent teams，通过 role-based collaboration 完成复杂任务； Flows 是 production-ready、event-driven workflows，提供 execution path control、state management、Python code integration 和 conditional branching。两者组合的目标是 balance autonomy with precise control。 证据在 Understanding Flows and Crews。

本篇结论：CrewAI 的核心 owner 是团队协作流程。 你先读 Agent、Task、Crew 和 Process，看到 Crews 怎样把自治协作包装成执行单元； 再读 Flow、@start、@listen、@router、state、persistence 和 human feedback， 看到它怎样把生产流程显式化。

证据边界。 CrewAI 源码固定到 a046e6a50be633f76a1b128b70ef54363aa01d7c。 本文只基于公开 README、docs 和源码；“团队协作流程”是对公开抽象 owner 的工程归纳，不是 CrewAI 官方术语。

一、先把 Crews 和 Flows 分开读

官方 docs 的 Crews 页说，crew 代表一组协作 agent，定义 task execution、agent collaboration 和 overall workflow 的策略。 属性表列出的不是底层 transport，而是 tasks、agents、process、manager_llm、function_calling_llm、memory、cache、embedder、 step_callback、task_callback、planning、knowledge_sources 和 stream。也就是说 CrewAI 先让应用把“谁做什么、按什么流程做、 怎样补记忆和知识、怎样输出”讲清楚。 证据在 Crew docs attributes。

Flows 页的定义则更像 workflow engine：Flows 用来组合 coding tasks 和 Crews，创建 structured event-driven workflows， 连接多个 task，管理 state，控制 execution flow，并支持 conditional logic、loops 和 branching。 这不是 Crews 的替代品，而是生产路径的显式控制层。 证据在 Flow docs overview。

Crews 解决自治协作

  • Agent: role / goal / backstory
  • Task: description / expected output
  • Process: sequential / hierarchical

Flows 解决生产控制

  • Decorators: @start / @listen / @router
  • State: dict 或 Pydantic model
  • Control: persistence / HITL / routing

二、Agent 是带角色的 worker，不只是 LLM wrapper

BaseAgent 的字段已经说明 CrewAI 的 agent 不是薄薄一层 completion adapter。它包含 role、goal、backstory、cache、 max_rpm、allow_delegation、tools、max_iter、llm、crew、knowledge、knowledge_sources、callbacks、apps、mcps、memory、 skills、execution_context 等字段。Agent 在这个基础上增加 function_calling_llm、step_callback、 use_system_prompt、templates、respect_context_window、planning_config、embedder、guardrail、a2a、executor_class 等能力。 源码在 BaseAgent fields 和 Agent fields。

真正执行 task 时，Agent.execute_task 的路径很清楚：先调用 _prepare_task_execution 注入日期、生成 task.prompt()、拼 schema、拼 context，再通过 memory recall 把相关记忆追加到 prompt；随后做 knowledge retrieval， 再调用 _finalize_task_prompt 准备 tools 和 training data，最后把 input、tool names、tool descriptions 和 human input flag 交给 agent_executor.invoke。 源码在 task prompt preparation、 memory retrieval、 execute_task 和 executor invocation。

这也是为什么 CrewAI 的 Agent.message() 很有意思：它不是绕过 task 和 crew 直接打一轮模型，而是临时创建一个 Task 和单 agent Crew，再 crew.kickoff() 返回 raw output。 源码在 Agent.message。 这说明 CrewAI 希望哪怕单轮消息也尽量落回 task / crew 语义。

三、Task 是工作契约，也是输出契约

Task 的字段把“要做什么”和“怎样收束结果”放在同一个对象里。它有 description、expected_output、agent、context、 async_execution、output_json、output_pydantic、response_model、output_file、tools、input_files、security_config、 human_input、markdown、guardrail、guardrails 和 guardrail_max_retries 等字段。 源码在 Task fields。

执行路径也强调契约。execute_sync 和 execute_async 最终都进 _execute_core： 先确认 agent，写入 prompt context，发 TaskStartedEvent，调用 agent 执行，再根据 BaseModel、output_pydantic、 output_json、guardrail 生成 TaskOutput，执行 callback，必要时写 output_file，最后发 TaskCompletedEvent。 源码在 sync and threaded async entry 和 _execute_core。

Task.prompt() 是最小工作契约的文本化：description 加 expected output；如果开启 markdown，就追加 Markdown 输出要求； 如果有 trigger payload 或 input files，也会把相关上下文加进 description。这和“聊天历史数组”不是同一种抽象。 源码在 Task.prompt。

四、Crew 是执行 owner，Process 只给它两种主路径

Process enum 目前只有 sequential 和 hierarchical 两个可用分支，consensual 还只是 TODO。Crew.kickoff 做 checkpoint、streaming、inputs、event runtime scope，然后按 process 分派到 _run_sequential_process 或 _run_hierarchical_process，跑完 after kickoff callbacks 和 post kickoff， 再计算 usage metrics。 源码在 Process 和 Crew.kickoff。

顺序模式直接执行 task list；层级模式先创建 manager agent，再执行同一批 task。自定义 manager agent 会被设置为 allow_delegation；如果没有自定义 manager，就用 manager_llm 创建一个带 delegation tools 的默认 manager。 源码在 sequential and hierarchical process。

_execute_tasks 是 Crew 的调度核心：逐个 task 准备执行数据，处理 conditional task，遇到 async task 就起 future， 遇到同步 task 之前会先收束已挂起的 futures，再根据 task context 聚合上游输出，调用 task.execute_sync。 最终 _create_crew_output 从有效 task outputs 里取最后一个 raw 作为 crew raw output，同时保留 tasks_output 和 token usage。 源码在 _execute_tasks、 context and final output。

Crew 的 planning 也不是外部 DAG 系统。_handle_crew_planning 会让 CrewPlanner 为每个 task 生成 plan， 再把对应 plan 追加到 task description。CrewPlanner 自己创建一个 planning agent 和一个输出为 PlannerTaskPydanticOutput 的 planning task。 源码在 _handle_crew_planning 和 CrewPlanner。

五、Memory、knowledge、tools 是提示词与副作用表面

CrewAI 对 memory 和 knowledge 的定位很务实。Agent 执行 task 时，memory recall 以 task description 为 query，取相关 memories 后追加到 prompt；knowledge retrieval 同时查询 agent knowledge 和 crew knowledge。Crew 侧的 query_knowledge 只是把 query 转给 crew-level knowledge base。 源码在 agent memory retrieval、 agent and crew knowledge lookup 和 Crew.query_knowledge。

tools 的接入也跟 process 有关。Crew 在 _prepare_tools 里根据 allow_delegation、hierarchical manager、 code execution、multimodal、apps、MCP、memory 和 input files 动态补工具。hierarchical 模式下 manager 通过 delegation tools 指挥任务 agent；非 hierarchical 且 agent 允许 delegation 时，也会把其他 agents 作为 delegation tools 注入。 源码在 _prepare_tools 和 delegation and platform tools。

六、Flow 是显式控制层，不是 Crew 的别名

现版本 crewai.flow.flow 已经只是兼容 re-export surface，文件注释说真正实现拆到了 crewai.flow.dsl、 crewai.flow.flow_definition 和 crewai.flow.runtime。公开 Flow 类继承 runtime Flow， 再组合 conversational mixin。 源码在 flow.py re-export。

DSL 装饰器是 metadata stamper。@start 会把方法标成 entry point，并可带 condition；@listen 把方法绑定到 route label、method reference 或 or_ / and_ condition；@router 标记 routing method，返回值会变成下游事件，显式 emit 或 Literal / Enum return annotation 会进入 definition。 源码在 @start、 @listen 和 @router。

runtime 侧，Flow 是 Pydantic model，支持 initial_state、name、tracing、stream、memory、input_provider 等字段， flow_definition() 会从 class lazily build static FlowDefinition。state 可以是 dict 或 BaseModel； _initialize_state 会更新输入并保证 dict state 有 id。 源码在 Flow class and definition 和 state initialization。

kickoff 是同步包装，最终进入 kickoff_async。异步路径会处理 checkpoint、streaming、input files、 restore_from_state_id、persistence hydrate、FlowStartedEvent、start methods 和 resumption；有 unconditional starts 时只跑它们， 否则所有 starts 都可作为 entry points，并可并行执行。后续 _execute_start_method 会执行 start method， 如果它也是 router，还会把返回值作为额外 trigger 继续触发 listeners。 源码在 Flow.kickoff、 kickoff_async setup 和 start method execution。

listeners 的执行规则也很明确：routers 先顺序执行，router result 成为新的 trigger；普通 listeners 再并行执行。 runtime 还跟踪 OR listener 的 firing 状态，避免 multi-event OR 条件重复触发。方法执行本身会发 started / finished / failed / paused 事件，支持 sync method 在线程池里执行，并在方法完成后调用 persistence。 源码在 _execute_method、 method persistence 和 router and listener dispatch。

@persist 和 @human_feedback 也都按这个模型工作：它们先把配置 stamp 到 class 或 method， 再由 Flow engine 在方法完成或 human feedback step 时读取 definition 并执行。也就是说 Flow 的生产特性没有绕开 graph， 而是挂在 graph method 生命周期上。 源码在 @persist 和 @human_feedback。

七、CrewBase 是项目层装配，不是另一个 runtime

docs 推荐用 YAML 配置 agents 和 tasks，再在继承 CrewBase 的类里通过 decorators 声明 @agent、 @task、@crew、@before_kickoff 和 @after_kickoff。 这套写法把配置、Python 方法和 crew 实例装配在一起。 证据在 CrewBase docs example。

源码上，@agent、@task、@tool、@callback 这些 decorators 都把方法包成带标记的 wrapper。 @crew wrapper 会先调用所有 task 方法和 agent 方法，收集去重后的 agents 和 tasks，再调用用户定义的 crew 方法， 并绑定 before / after kickoff callbacks。CrewBaseMeta 则在实例化时加载配置、映射变量、收集原始方法元数据。 源码在 project decorators、 @crew wrapper 和 CrewBaseMeta。

八、和前几篇放在一起看

框架 先读的 owner 最容易误读的点
AgentScope agent turn ledger 与 OpenAI API 适配。 不是只有 Chat Completions wrapper，也要看 Responses API 事件化输出。
ADK Python code-first Agent + Workflow + Runner。 不是只有 graph DSL，自主 agent 和确定性 workflow 共用运行边界。
Agno AgentOS platform control plane。 不是更大的 agent dataclass，而是 API、storage、approval、RBAC 和 interface 平台层。
AutoGen / MAF message runtime 到 production orchestration。 AutoGen 进入 maintenance mode 后，新项目应该从 MAF 的 Agent、Workflow、Hosting 读起。
CrewAI Agent / Task / Crew / Flow。 不要先找底层 bus；它先把团队自治和生产控制建模给应用开发者。
