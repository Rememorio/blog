Agent Framework Source Notes · Part 8

tRPC-Agent-Go Turns Go Agents Into A Service Runtime

The Eino chapter read how Go agents can live inside composable execution graphs. tRPC-Agent-Go moves further into service runtime: Runner owns sessions and invocation boundaries, GraphAgent owns deterministic workflows, tools / skills / codeexecutor / artifacts own side effects, and AG-UI, A2A, and the OpenAI-compatible server own protocol surfaces. The second half then focuses on Rememorio's summary and memory path.

Topic: tRPC-Agent-Go Framework: Runner / Graph / Skill / Server Focus: summary / memory / session_load

If you look only at memory and summary, tRPC-Agent-Go can look like a long-context plugin for Go agents. The source reads larger than that. It names the owners a production agent needs: who owns one run, who owns deterministic workflow, who owns tools and code execution, who owns file artifacts, who owns frontend protocols, and who owns durable state.

The image above is the second-half focus: long context. Imagine an internal support agent helping the same user over several days. On day one it reads logs. On day two it calls ticketing tools. On day three the user says, "the same error as yesterday." The framework now has to run as a service, compress old session history, persist durable facts, and recover raw evidence when needed.

Reading contract. This chapter first maps the framework owners, then follows the long-context path where Rememorio's work is densest. It is not a module-name list. It asks what Runner, Graph, tools, skills, codeexecutor, artifact, server, and memory each take off application code.

Evidence boundary. Source links are pinned to public snapshot d3b50fd90d60b4ece8a78e89cf890a4f06d78235. Terms such as owner, ledger, and projection are engineering summaries over the public runner, agent, graph, tool, skill, artifact, server, summary, memory, and processor code.

1. Start With The Runtime Owners

The README does not position this repository as a memory library. It calls tRPC-Agent-Go a Go framework for building production agent systems: LLM agents, graph workflows, tool calling, session and memory state, knowledge retrieval, self-evolution, evaluation, OpenTelemetry, and A2A / AG-UI / MCP integration live in one Go-native stack. The same shape appears in the package table. Sources: README feature map and package table.

Runtime owner What it owns for application code Beginner reading First source
Runner / Invocation App, user, session, message, agent, memory service, artifact service, plugins, and run options for one request. Before the model runs, the runtime builds the execution context for this turn. runner fields, newRunInvocation
Agent family LLMAgent owns model, tools, planner, and sub-agents; Chain/Parallel/Cycle compose multiple agents into execution shapes. An agent can be a model loop or an orchestrator over other agents. Agent interface, LLMAgent, ParallelAgent
GraphAgent / StateGraph Deterministic nodes, conditional routing, multi-branch fan-out, joins, LLM nodes, tools nodes, agent nodes, checkpoint and interrupt options. A workflow graph moves out of the prompt and into verifiable Go code. StateGraph, GraphAgent
Tool / Skill / CodeExecutor / Artifact Go functions, MCP tools, SKILL.md workflows, code execution, and versioned files all enter one controlled capability surface. The model can act through bounded interfaces, and generated files can be tracked instead of pasted into text. tool, skill.Repository, artifact.Service
Server plane The same Runner can be exposed through AG-UI frontends, A2A interoperability, and OpenAI-compatible chat completions. Protocol adapters are part of the runtime boundary, not just examples. server/agui, server/a2a, server/openai

The important point is not that the repo has many packages. It is that tRPC-Agent-Go avoids putting every production concern into one giant agent class. The long-context design later in this chapter is a collaboration between Runner, Session, Summary, Memory, and request processors.

2. Graph, Skill, CodeExecutor, Artifact, And AG-UI

The names are easy to flatten, so read their ownership carefully. Graph is not asking the model to "make a plan." AddNode, AddEdge, AddConditionalEdges, AddMultiConditionalEdges, and Compile turn a workflow into executable Go structure. GraphAgent then puts that compiled graph back behind the common agent.Agent interface. Sources: AddNode / LLM / tools / agent nodes, edges and compile, and GraphAgent.Run.

Skill is not just a prompt-snippet library either. A skill is a folder with SKILL.md plus optional docs and scripts. FSRepository scans, refreshes, and loads skills by name. LLMAgent then registers progressive-disclosure tools such as skill_load, skill_list_docs, and skill_select_docs, plus the compatibility execution path with skill_run / skill_exec when configured. Sources: NewFSRepository / Refresh, skill tool profiles, and skill_load.

CodeExecutor and Artifact separate "run code" from "store generated files." The executor owns ExecuteCode and code-block delimiters. The artifact service owns save, load, list, version, and delete under app/user/session/filename. SaveArtifactHelper and LoadArtifactHelper let the code-execution layer find the artifact service through context, so generated images, reports, and intermediate files do not need to be inlined into model text. Sources: CodeExecutor, LoadArtifactHelper, SaveArtifactHelper, and artifact.Service.

The protocol layer is part of the same story. server/agui wraps a Runner into an AG-UI runner, resolves frontend run input, app/user/state/run options, and translates internal events into AG-UI events. server/a2a builds an AgentCard and message processor. server/openai exposes a Runner through a /v1/chat/completions style HTTP handler. Sources: AG-UI runner, AG-UI run input, A2A processor, and OpenAI server.

Map the runtime first, then memory makes sense. Summary and memory are not isolated features. They appear naturally once Runner persists events, processors build model requests, tool surfaces expose recall, and server adapters keep sessions alive.

3. Long-Context Focus: Start With Three Ledgers

Many agent frameworks expose a feature called memory. The word is too broad. In tRPC-Agent-Go, the source is clearer if you read three ledgers first: session events, session summary, and durable memory.

Ledger What it stores How it reaches the model First source
Session events User messages, assistant events, tool results, state deltas, and tracks for one session. Normally appended in event order; after summary, only events after the cutoff are appended. Session fields
Session summary A compressed text record for old events under a filter key, plus the included boundary. The content processor injects the summary and then appends only post-cutoff messages. Summaries, appendSessionMessages
Memory Cross-session facts and episodes scoped by app and user, with kind, time, topics, and metadata. It can be preloaded into context or fetched on demand through memory_search and memory_load. memory.Service, Memory / Entry

The core distinction is simple: summary is not long-term memory, and memory is not a chat transcript summary. Summary keeps the current session runnable. Memory carries stable facts into future sessions.

4. Runner Connects Long-Context Ledgers To The Runtime

The runner is not a thin caller around the agent. During Run, it gets or creates a session, attaches the current user message, session service, memory service, agent, run options, and plugins to the invocation, then lets the agent execute. Sources: Run and newRunInvocation.

After events are persisted, the runner decides which background ledgers need work. handleEventPersistence writes eligible events to the session and queues summary work by event filter key. When the runner completion event is handled, it queues auto-memory extraction as well. Sources: handleEventPersistence and runner completion.

The runtime collects the ledgers automatically. Application code does not have to write a manual "if context is long, summarize, and maybe extract memories" branch after every turn.

5. Summary Compresses The Current Session

Summary starts with a gate. The public summarizer interface exposes ShouldSummarize and Summarize, with a context-aware variant for invocation-aware decisions. Source: SessionSummarizer.

Thresholds First

The gate can combine event count, token count, elapsed time, and context-window pressure. Static options include token, event, and time thresholds; WithContextThreshold can inspect invocation context, model information, and context size dynamically. Sources: threshold options and WithContextThreshold.

When async summary is configured, jobs go into a hash-routed worker queue. If the queue or worker path cannot take the job, the service can fall back to synchronous summary. Source: AsyncSummaryWorker.EnqueueJob.

Summarize Only The Delta

The internal summary path takes a per-session/filter lock, reads the previous summary, computes the delta after the previous boundary, prepends the previous summary as context, and builds a temporary filtered session for the summarizer. That avoids repeatedly summarizing the whole ledger. Sources: SummarizeSession, buildSummaryInput, and summary lock.

The summarizer then filters events, skips recent turns when configured, extracts user/assistant content, tool calls, and tool results into conversation text, and asks the model for the compressed record. Sources: Summarize, filterEventsForSummary, and extractConversationText.

Inject Summary, Keep Raw Events

The resulting summary is written back to the session summary store with a boundary. On the next model request, the content processor injects the summary, then appends only messages after the cutoff. It does not delete the raw session events. Sources: writeSummary, appendSummaryContext, and sessionMessagesAfterCutoff.

Cache-Safe Forking Protects Request Shape

A normal summary request can use a standalone summary prompt. Cache-safe forking is more careful: if a parent model request is available, WithCacheSafeForking clones that request and appends a compacting user message. This preserves provider-facing request shape when prompt caches, reasoning fields, tools, or headers matter. Without a parent request, it falls back to the standalone prompt. Sources: WithCacheSafeForking and request clone helpers.

Pre-LLM context compaction follows the same runtime idea. Before a model call, the flow can detect context pressure, create a summary synchronously, attach the parent request to the summary context, and rebuild the model request. Sources: maybeCompactContextBeforeLLM and runContextCompaction.

6. Memory Persists Durable Facts

Memory has a different contract. memory.Service exposes Add, Update, Delete, Clear, Read, Search, Tools, EnqueueAutoMemoryJob, and Close. Entries are facts or episodes scoped by app and user. They are not a compressed copy of the current session transcript. Sources: Service and Kind / Entry.

Tools Are Explicit

Built-in memory tools are named memory_add, memory_update, memory_delete, memory_clear, memory_search, and memory_load. Tool implementations fetch the memory service, app name, and user id from invocation context. Search and load return structured entries rather than dumping every memory into the prompt. Sources: tool names, memory_search / memory_load, and context lookup.

Search is deliberately shaped as retrieval, not prompt stuffing. SearchOptions supports kind, time windows, result count, similarity threshold, ordering, dedupe, hybrid search, and RRF. Sources: SearchOptions and buildSearchOptions.

Auto Memory Runs After The Turn

Auto memory is queued when the runner completes, not on every individual sentence. If a memory service and extractor are configured, the runner hands the session to the auto-memory worker. Sources: enqueueAutoMemoryJob and NewMemoryService.

The worker reads the last extraction point, scans only the delta, keeps user and assistant text, excludes tool messages and tool calls, then checks thresholds. Sources: AutoMemoryWorker.EnqueueJob and scanDeltaSince.

Extraction is also retrieval-aware. The worker builds a query from user messages, searches relevant existing memories, asks the extractor model for add/update/delete/clear operations, reconciles operations, and executes only enabled actions. Sources: createAutoMemory, Extract, and executeOperation.

Preload Gives The Model A Small Durable Background

Preload memory is another model-visibility path. The content processor can format selected memories into a prompt block with usage guidance. It does not mean the entire memory store is appended to every request. Sources: WithPreloadMemory and preload memory prompt.

Memory is durable knowledge, not session compression. Current-session compression belongs to summary. Durable facts and episodes belong to memory.

7. session_search And session_load Recover Hidden History

Once summary takes effect, the main model context contains summary plus the post-cutoff delta. The raw old events are still in the session ledger. session_search can search current visible history, current hidden history, and other scopes. The current_hidden path uses the summary boundary to search old events hidden by summary. Source: searchCurrentHidden.

session_load then loads a raw event window around the selected anchor. The window is built from ordered events, so the model can recover exact local detail rather than guessing from the summary. Sources: resolveLoadAnchorEventID and EventWindowFromOrderedEvents.

8. Place tRPC-Agent-Go Back On The Series Map

Eino asks how Go components, streams, interrupts, and agent loops become a composable graph. tRPC-Agent-Go goes one layer further: it puts Runner, GraphAgent, the tool surface, Skills, code execution, artifact storage, AG-UI/A2A/OpenAI servers, and long-context state into one Go service runtime. The second half of this chapter focused on the part most often misread: summary, memory, and hidden-history recall.

Misread Better reading
Memory means summarizing the chat transcript. Summary compresses the current session; memory persists cross-session facts and episodes.
Once summary exists, old events can be deleted. Summary changes the main model view. Raw events still serve session_search and session_load.
Auto memory writes every sentence into long-term memory. It runs after completion, scans deltas, checks thresholds, retrieves existing memories, then extracts operations.
Long-context models make summary unnecessary. Summary still governs cost, cache shape, tool transcripts, and recovery boundaries.

The conclusion has two layers: overall, tRPC-Agent-Go is a Go agent service runtime; inside that runtime, long-context ownership is not one memory switch. It is two ledgers plus a recall path. Runner connects the owners to execution, Graph / Skills / CodeExecutor / Artifact / Server plane expand the production shape, summary keeps the current session runnable, memory preserves durable facts, and session_load can recover raw history hidden by summary.
