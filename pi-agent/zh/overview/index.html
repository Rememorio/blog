Pi 为什么把 Coding Agent 做成可扩展的 Harness

Pi 是一个开源的终端编程 Agent：你交给它代码任务，它调用模型和工具，执行修改与测试。支撑这段工作的 Harness 负责循环、进度和会话；本篇从一次配置改造出发，读懂这些机制怎样配合。

主题：Pi Agent Harness 主线：pi-ai → agent-core → coding-agent 重点：loop / session tree / compaction / extensions

Pi 连续阅读的第一站：本篇跟着代码修改与测试建立运行图；下一篇追踪测试留下的长日志，第三站处理同一次测试产生的三份报告。三篇分别回答谁运行任务、怎样重建输入、怎样在工具结果进入消息前筛选数据。

一、Pi 怎样接手一次代码修改

Pi 是一个开源的终端编程 Agent。安装并配置模型后，你在项目目录运行 pi，就可以用自然语言交给它任务。例如：“把配置读取改成异步，保持公共接口，再跑测试。”

模型首先需要看到文件。它可以返回一个 read 工具调用，里面包含工具名称和文件路径等参数；Pi 执行读取，把结果交回模型。模型随后提出 edit 修改，等修改完成，再通过 bash 运行测试。测试失败时，模型根据错误继续修复。这种“模型提出操作、程序执行并返回结果”的协作，就是本文要追踪的工具循环。

任务持续运行时，Pi 还要显示进度、接住用户新输入、保存记录，并在输入太长时整理历史。支撑这些工作的程序机制称为 agent harness。Pi 的核心协调模型、工具、事件和会话；命令审批、任务规划、子 Agent 协作等工作方式可以通过扩展加入。

二、Harness 先接住哪四件事

先分清三个参与者：模型生成回答或工具请求；provider 提供调用模型的 API；runtime（运行时） 是 Pi 中发起请求、执行工具和保存状态的程序。一次任务可以连续调用模型很多次。

  • 接模型：把不同 provider 的消息、工具调用和流式返回转换为统一格式。
  • 跑循环：执行模型提出的工具操作，交回结果，并判断是否安排下一次模型请求。
  • 报进度：把文本更新、工具开始和结束等变化发成事件，供终端或接入 Pi 的程序显示。
  • 保会话：保存消息、工具结果、分支和摘要，支持恢复当前工作路径。

这里的会话（session）是一段可保存、可恢复的工作历史，可以包含多个用户任务；上下文（context）是某一次模型请求所用的输入。它包括行为指令（system prompt）、工具说明，以及从会话中选出的消息。同一份会话可以为不同请求组装出不同的上下文。

三、同一个改造任务怎样走完

  1. Pi 装配选定模型、文件与命令工具、行为指令，以及已有的会话记录。
  2. 模型请求读取配置文件，Pi 执行工具并记录结果。互不依赖的文件读取可以并行。
  3. 模型根据文件内容提出修改；收到修改结果后，再请求执行依赖这次修改的测试。
  4. 用户中途补充“不要改公共接口”，Pi 把这条改变当前方向的输入排入 steering 队列，在下一次模型调用前交给模型。
  5. 测试失败后，模型读取错误并继续修复。工具处理结束后，扩展仍可补充验证要求并请求继续；最终还要核对测试结果与代码差异。
  6. “做完后再补 changelog”这类后续任务进入 follow-up 队列，等当前工具与 steering 工作处理完再开始。输入过长时，Pi 用旧内容的摘要和近期记录继续任务，这称为 compaction（上下文压缩）。
  7. 原始记录保存在会话里，用户可以恢复、回看，或从较早位置开始另一条工作分支。

后文把“一次模型响应及其提出的工具调用结果”称为一个 turn（回合）。底层循环可以连续执行多个回合，这一段执行称为 run。会话会继续保存这些 run 的记录，因此结束一次循环后仍可接收新任务。

同一任务的记录怎样得到用在什么地方
持久会话记录持续追加消息、工具结果和摘要，保留已走过的分支。回看、恢复与排查。
当前分支从会话树中选出当前所在位置及其祖先记录。决定这次继续哪一条工作路径。
本轮模型输入从当前路径选取消息，应用摘要、内容编辑和请求转换。发送给模型，供它决定下一步。

源码依据：运行结构对应 Pi 1.0.0；摘要生成与截断恢复按后续源码快照核对。下文跟随本地终端产品的执行与会话保存路径，源码链接固定到对应版本。

四、从模型接入到终端：源码中的四层分工

4.1 从 provider 到终端，每层只接一类责任

源码把这条运行路径拆成四层：pi-ai、pi-agent-core、pi-coding-agent 和 pi-tui。可以沿四个问题定位代码：谁转换模型 API 格式，谁重复调用模型与工具，谁管理文件工具和会话，谁把进度呈现在终端。

层 它拥有的责任 它不负责决定什么 第一眼源码
pi-ai 统一 model、provider、消息 content block、tool schema、usage 和流式 assistant event。 不决定 coding agent 应该调用哪个工具，也不保存会话树。 Provider / Models
pi-agent-core 拥有 agent state、turn 事件、模型调用、工具批次、steering 和 follow-up 队列。 不知道文件工具长什么样，也不知道会话落在哪个目录。 message 与 event contract
pi-coding-agent 装配 read/bash/edit/write、system prompt、resources、session、compaction、extensions 和运行模式。 不把 TUI 当成唯一入口，也不把某个 provider 写死在产品层。 createAgentSession
pi-tui / modes 把同一事件流呈现成交互终端、print/JSON、RPC，或让 SDK 嵌进别的应用。 不重写 agent loop；界面只是 runtime 的消费者。 四种运行入口

AgentSession 是产品层协调一次会话的对象，负责装配模型、工具和扩展，并处理压缩与恢复；它使用的 SessionManager 负责记录、分支导航和上下文重建。终端之外，应用可以用 SDK 直接创建 AgentSession，也可以通过 RPC 用逐行 JSON 交换命令、响应和事件。这些入口复用同一套执行与会话机制。

1.0 中的旧接口与实验性包

本文用 Harness 概括产品的运行机制。1.0 已从 agent-core 移除旧实验性 AgentHarness 接口；独立的 pi-durable 仍标为实验性，源码中的客户端／服务端实现也未进入默认发行路径。下文继续跟随本地会话文件。

4.2 核心维持运行一致性，扩展选择工作方式

如果核心只是把文本传给模型，它无法解释三件事：工具结果为什么能和原始 tool call 对上， 用户中途的新消息什么时候进入，进程重启后为什么能从同一分支继续。Pi 把这些都留在核心， 因为它们决定了运行是否可重放；至于“每次 bash 都弹确认框”还是“整个进程运行在容器里”， 则属于具体环境的安全策略。

Pi 的核心边界： 保证一次 agent run 在消息、事件、工具结果和会话记录上自洽；不替所有使用者规定工作流与安全交互。

五、一次任务怎样经过多轮模型与工具调用

5.1 从一次模型响应走到下一次请求

回到“改异步并跑测试”的任务。第一回合模型请求 read 并收到文件内容；第二回合请求 edit 并收到修改结果；第三回合才通过 bash 测试这次修改。下一回合再根据测试结果修复或回答。每次响应用 stopReason 标明停止原因，并用内容块携带文本或工具请求；Pi 根据这些结果安排后续执行。

正常工具路径可以按五步阅读；错误、取消与主动停止另有出口：

  1. 注入等待中的输入，在每次请求的 prepareRequest 阶段重建有效上下文。
  2. 调用 provider，流式得到完整 assistant message。
  3. 若有 tool call，完成工具批次并写回结果。
  4. 调用 finishTurn 决定默认调度、继续或结束，然后发出低层 turn_end。
  5. 处理工具后续请求、steering 与 follow-up；仍无后续请求且未要求继续时，发出低层 agent_end。

这正是 runLoop 的内外两层循环：内层处理工具与 steering，外层让“本来已经结束的 agent”还能接住 follow-up。

低层 agent_end 只结束这一段循环。外层 AgentSession 还可能进行错误恢复，或通过 agent_before_settle 让扩展补充记录并继续。因此既不能把它直接读成整个会话已空闲，也不能读成质量通过。即使测试从 exit code 1 修复到 0，仍要检查 diff 是否改变公共接口，再由 CI 或用户接受结果。

下一轮并不直接复用刚才的请求。prepareNextTurn 可以更新上下文、模型与 thinking 设置；每次 provider 调用前的 prepareRequest 又从 SessionManager 重建有效消息。coding harness 会把新工具结果计入预算，必要时先压缩。准备期间新到的 steering 也会再次检查。实现见 请求前上下文重建。

finishTurn 的 continue 保证还有一次模型请求；工具、steering 或 follow-up 已经带来的下一次请求可以满足它，不会额外重复一次。end 则结束当前低层 run，不再消费队列。错误和取消仍走硬退出，不能靠返回 continue 强行续跑。coding-agent 的 turn_end 与 agent_before_settle 扩展还可提交记录草稿，经预览和校验后按序落盘；详细时序见 上下文专题与 agent loop。

5.2 工具可以并行完成，结果仍按原调用顺序写入

假设模型一次请求同时要读取两个互不相关的文件。Pi 默认可以并行执行工具；但“并发完成顺序”和 “assistant 原始 tool call 顺序”不是一回事。快的工具可以先发 tool_execution_end，最终写入 context 的 tool-result messages 仍按模型提出调用的顺序排列。 这样 UI 能及时更新，下一轮模型又能拿到稳定的调用—结果配对。

具体实现先逐个做参数校验和 beforeToolCall preflight，再把允许的调用并发执行； Promise.all 收集后，按数组原顺序发出 tool result message。 如果配置 toolExecution: "sequential"，或任一工具声明 executionMode: "sequential"，整个 batch 会退回顺序执行。并行 preflight 被中断后，已准备但尚未启动的工具也会检查 abort，避免取消后继续产生副作用。 参见 executeToolCalls。

实时事件顺序

tool A start
tool B start
tool B end
tool A end

适合 UI 展示真实进度。

Tool Call 与结果的写入顺序

assistant: [A, B]
toolResult: A
toolResult: B

保持调用与结果的稳定对应。

另一个容易忽略的失败边界是输出截断。如果 assistant message 因长度上限停止，残缺 JSON 有时仍可能被“尽力解析”成看似合法的参数。Pi 不执行这些调用，而是为整个批次生成错误结果， 让模型下一轮重新发出完整参数。 截断工具调用处理 保护的是副作用完整性，不只是 parser 成功率。

5.3 中途调整方向与排队后续任务

当 agent 正在跑测试时，你输入“不要改公共接口”，这是 steering：当前 assistant turn 和已经提出的工具调用会先正常结束， 这句话随后在下一次模型调用前进入 context。你输入“做完后再补一个 changelog”，则更像 follow-up： 只有当原任务已经没有工具和 steering 可处理时，它才开启下一轮。

这个边界避免了两个常见错误。第一，steering 不会把正在执行的工具凭空抹掉； 第二，follow-up 不会在主任务中途抢占上下文。低层 contract 在 getSteeringMessages / getFollowUpMessages， 产品层又把 Enter 与 Alt+Enter 映射到两类队列。

六、每次模型请求的输入怎样组装

6.1 一份运行历史里可以有模型根本不该看到的记录

Pi 在 agent 层使用可扩展的 AgentMessage。coding-agent 先从会话重建消息：选当前分支和压缩范围，应用上下文编辑，再交给 agent 层转换。直接改写 agent.state.messages 不会持久改变下次请求，因为 prepareRequest 会重新读取会话记录。最后才执行可选 transformContext 与必须的 convertToLlm：

SessionManager.buildSessionProjection()
  -> prepareRequest()
  -> AgentMessage[]
  -> transformContext()   // 压缩、裁剪、注入外部上下文
  -> AgentMessage[]
  -> convertToLlm()      // 过滤 UI-only 项，转换自定义消息
  -> provider Message[]

这个边界写在 streamAssistantResponse。 它意味着“会话里存在”不自动等于“下一轮发给模型”。扩展的普通 CustomEntry 可以持久化计数器却完全不进入 context；CustomMessageEntry 才是显式进入 model-visible view 的类型。

工具集合本身也进入可重放的历史。每次模型请求前，declareToolChanges 比较历史已声明的工具与当前可执行工具，把差异写成 system message 的 toolsAdded / toolsRemoved。例如扩展撤下 bash 后，后续请求看到撤下记录，而不是继续相信旧工具目录；仅仅修改内存中的工具数组不足以解释这一变化。

长日志写入会话后，后续请求可以通过持久的 context_edit 或请求时转换缩短内容。两者的保存位置与恢复行为在下一篇的请求重建流程中展开；这里先保留“会话记录 → 本次消息 → provider 请求”这条分工。

6.2 provider 差异停在 pi-ai，上层只看统一事件

Anthropic、OpenAI Responses、OpenAI-compatible chat、Google 等 provider 的 wire shape 不一样， 但 agent loop 消费的是统一的 AssistantMessageEventStream。流开始时先把 partial assistant message 放进当前 context；text、thinking、tool-call delta 持续替换这条 partial；done/error 到来后再落成 final message。 对上层来说，provider 变了，message_start → message_update → message_end 的生命周期不变。

pi-ai 让工具循环与 provider payload 解耦，并作为独立包供其他应用复用。 coding agent 还可以通过 extension 注册新 provider 或覆盖 base URL。 registerProvider 是产品层重新接入 provider 的扩展点。

6.3 每次请求还可以选择不同的实际模型

实验性的 virtual models 让用户选择一个虚拟模型，由扩展在请求时选定实际 provider、model 和 thinking。会话保留虚拟选择，assistant 记录实际执行模型；路由状态可沿分支保存。若实际模型上下文窗口较小，runtime 会按该模型检查压缩。切换模型可能影响缓存复用与消息兼容性，所以“能够路由”不能直接推出成本或质量更好；应比较同一任务的实际结果和用量。

七、会话树怎样保留分支与恢复路径

7.1 id + parentId + leaf 把“回到过去”变成移动指针

同一任务可能需要试两种实现。Pi 用 JSONL 保存会话：文件每一行是一条 JSON 记录，源码称它为 entry。记录以追加方式形成树，每条都有 id 和指向前一条记录的 parentId；leafId 标记当前所在位置。从这个位置沿 parentId 回到根，就能选出当前有效分支。

{"type":"message","id":"m1","parentId":null,"message":{"role":"user","content":"改成异步"}}
{"type":"message","id":"m2","parentId":"m1","message":{"role":"assistant","content":[...]}}
{"type":"message","id":"m3","parentId":"m2","message":{"role":"toolResult",...}}
{"type":"message","id":"b1","parentId":"m1","message":{"role":"user","content":"保留同步兼容层"}}

这是简化后的 shape，不是完整 session 文件。m3 与 b1 是从不同位置继续的两条路； 旧记录没有被改写。SessionManager.branch() 只是把 leaf 移到较早 entry， 下一次 append 自然成为它的新 child。 分支与 tree 构造 实现了这种追加与导航方式。

会话分支保留的是工作历史。/tree 移动当前记录位置，已经执行的文件修改、命令和外部 API 操作仍然保留。试验另一条代码实现时，应使用 Git 分支或 worktree 管理文件版本；工具隔离由进程环境或扩展配置。

7.2 /tree、/fork、/clone 解决的是三种不同问题

操作 记录怎么变 适合的场景
/tree 留在同一个 JSONL，移动 leaf；可选把离开的分支总结到新位置。 在同一任务里试另一种实现，同时保留两条路径。
/fork 把选定 active path 复制成新的 session 文件，并把旧 user prompt 放回编辑器。 从过去的问题开始一个独立实验。
/clone 复制当前 active path 到新 session，编辑器为空。 保留当前上下文，但把后续工作拆成另一份会话。

/tree 还有一层容易读反的行为：如果用户选择总结离开的旧分支， navigateTree() 先找到旧 leaf 与目标路径的 common ancestor，收集离开路径上的 entries； summary 生成后，不是挂在旧 leaf 后面，而是作为 BranchSummaryEntry 追加到新的导航位置。 这样未来从新分支继续时，模型能知道“另一条路试过什么”，却不必把整条旧分支重新塞进 context。 参见 navigateTree。

八、用摘要与近期记录继续长任务

模型每次能接收的输入长度有限，通常用 token 计量。长日志和多轮修复逐渐占满这个窗口时，Pi 可以把较早内容整理成摘要，保留近期消息，再组装后续请求。原始会话记录仍可回看。

8.1 触发以后，先找到不会拆散 Tool Call 与结果的位置

当 context token 超过 contextWindow - reserveTokens，或用户主动执行 /compact，Pi 先重建当前有效输入，再从其中向前选择保留范围。已经应用的 context_edit 会影响摘要材料和长度估算；原始长日志不会仅因为还在 JSONL 中就重新进入摘要。keepRecentTokens 尽量保留近期内容，但切点不能落在 tool result 上，避免留下孤儿结果。

切点必须兼顾消息角色和完整 turn。若一个 turn 自己已经超出保留预算，可以单独总结早期 turn prefix；若尾部工具结果很大，则连同前面的 assistant tool call 一起保留。keepRecentTokens 是近似预算。当前 preparation 使用 findProjectedCutPoint，根据每条 entry 实际贡献的消息选择范围，同时处理不贡献模型内容的记录。

8.2 Summary 是 model context 的检查点协议

默认 summary path 依次做四件事：

  1. 从已应用编辑的有效消息中取摘要材料，再把自定义消息转换并序列化成带角色标签的文本。
  2. 截短过大的 tool result，避免 summary request 自己再次撑爆 context。
  3. 要求模型只输出 Goal、Constraints、Progress、Decisions、Next Steps、Critical Context，不继续原对话。
  4. 额外累计 read/write/edit 的文件清单，作为结构化标记附在 summary 后面。

这些步骤分别由 serializeConversation 和 generateSummaryWithUsage 实现。这样 summary 的目标不是写一段好看的回顾，而是给另一个模型留下可继续推理的文本检查点。 它只恢复本轮模型输入，不恢复工作区文件、后台进程、工具内部状态或已经发生的外部副作用。

摘要请求的输入、输出与安装检查，集中在下一篇的摘要请求协议中；本篇继续看摘要怎样成为会话记录。

8.3 写入新的 Entry，再重建下一轮模型输入

Summary 成功后，AgentSession 追加 CompactionEntry { summary, firstKeptEntryId, tokensBefore, details }，再通过 buildSessionProjection() 刷新状态。旧消息仍在 JSONL。新的输入包含压缩时的 system 检查点、最新摘要、保留范围内有效消息与之后的新记录；内容编辑仍参与重建。下面省略无关元数据：

persistent JSONL:
M1 -> A1 -> T1 -> M2 -> A2 -> T2 -> C1

C1 = {
  type: "compaction",
  summary: "...",
  firstKeptEntryId: "M2",
  tokensBefore: 48210,
  systemMessage: { role: "system", content: "...", ... }
}

下一轮 model-visible view:
[systemCheckpoint(C1), compactionSummary(C1), M2, A2, T2]

这也是 Pi 与“直接把旧数组替换成摘要”的关键差别。后者一旦摘要漏掉细节，原始记录就已经消失； Pi 的 Compaction 会有损地缩短模型输入，但原始历史仍可通过 /tree 查看。 写入与重建发生在 AgentSession.compact， 投影规则在 buildContextEntries。

8.4 自动恢复与再次压缩分别有自己的停止条件

自动压缩区分“主动腾空间”和“中断后恢复”。threshold 跨过预算就压缩，不重跑已经完成的回答；overflow 既可能来自上下文溢出，也可能来自可恢复的长度截断。失败或截断的 assistant message 会从重试输入中移除，但仍留在会话历史里，随后最多执行一次压缩并重试。若回答已正常完成，只压缩而不重跑。无 provider usage 时还可以按消息大小估计，压缩前的陈旧 usage 则不能触发刚压完后的第二次压缩。 _checkCompaction 选择恢复原因；_runAutoCompaction 执行并安装结果。等待中的 steering/follow-up 在压缩后仍可继续处理。

再次压缩从当前重建结果出发：旧摘要与上次保留的尾部已经在这份结果中，新摘要再吸收后来进展，不需要重新把所有原始记录拉回来。输入被 context_edit 或 compaction 改过以后，较早 assistant 的 usage 已不能代表当前长度；estimateProjectedContextTokens 会按有效消息重新估算。失败 assistant 的省略也用持久 context_edit 表达。恢复时，runtime 从当前有效输入找出该 assistant 的 toolCallId，以及下一条 assistant 之前的配对结果，一起写入省略记录；这让当前 run 与恢复后的下一次请求都维持调用和结果的配对。见 prepareCompaction与 上下文专题。

九、Extension 可以介入哪些运行步骤

9.1 内置能力也通过扩展进入产品

在 v1.0.0，MCP、codemode 和 tool_search 已是内置扩展。MCP（Model Context Protocol）是一种连接外部工具服务的协议，在这里负责接入服务与发现工具；codemode 让模型用 JavaScript 组合调用并过滤结果；tool_search 把选中的工具声明加载到后续请求。它们增加了默认产品能力，却不需要把全部行为塞进低层 agent-core。入口和结果流详见 Codemode 与 MCP 专题。

Extension 是在 Pi 进程内执行的扩展程序。它可以注册工具、命令、provider 与 MCP 服务，也能处理模型请求、工具执行和会话事件。turn_end 与 agent_before_settle 还允许返回追加记录和续跑草稿。计划流程、子 Agent 编排和权限交互仍可由扩展选择；产品默认能力与核心循环由不同层次实现。

想增加的能力 介入哪个运行步骤 必须保持的行为
危险命令确认 tool_call / beforeToolCall 被拒绝的调用要变成明确 tool result，不能静默消失。
自定义 compaction session_before_compact 仍要提供 summary、first kept entry 和 token boundary，恢复路径不能断。
plan mode / sub-agent custom tool、message、entry、command、event 子流程的结果最终仍通过 agent message 与 session record 回到主线。
MCP 与脚本工具编排 内置 MCP、codemode、tool_search；可由扩展替换。 嵌套调用仍经工具 hook，发现与声明沿明确规则变化。
新 provider registerProvider / custom stream 上层仍消费统一 assistant message event。

9.2 Skills 是按需说明书，Extensions 是可执行 runtime code

Skill 以 SKILL.md 表达说明、步骤和资源， 默认把 name/description 放进 system prompt，模型需要时再读取正文；Extension 则是运行在 Pi 进程里的 TypeScript， 可以直接注册工具、修改事件或写 session state。 skill metadata validation 与 formatSkillsForPrompt 说明前者是渐进披露；后者拥有完整代码权限。

一个 Pi Package 可以同时带 extension、skill、prompt 和 theme。扩展在宿主进程中执行代码，skill 则可能指引模型调用有副作用的工具，因此不能根据包的外观判断可信程度。安全文档 要求加载前审查扩展和包；可扩展性带来的代码权限需要由部署环境约束。

十、项目加载、工具权限与运行隔离怎样分工

10.1 启动时信任项目，与每次工具调用是否允许，是两道门

Project trust 控制项目 settings、MCP 配置、extensions、skills、prompts、themes 与 system-prompt 文件等受保护资源是否加载。默认需要信任决定，但已有决定、命令行参数和扩展可以改变交互。它防止项目悄悄加载可执行扩展，不限制会话启动后工具的操作权限。Security 文档 还列出两个例外：project sessionDir 在信任判断前读取；AGENTS.override.md、AGENTS.md 和 CLAUDE.md 等上下文文件，除非禁用 context loading，否则不受该信任决定阻止。

beforeToolCall 与扩展的 tool_call 事件可以在执行前阻止工具调用。默认发行版没有逐次允许、拒绝或询问的权限策略；未配置权限扩展或运行隔离时，read、write、edit、bash 使用启动 Pi 的用户与进程权限。

10.2 真正隔离要落到进程或工具执行环境

Pi 文档列出三种隔离方式：整个进程放进 Docker；整个进程进入 OpenShell 这类 policy-controlled sandbox； 或让 Pi 与 provider auth 留在宿主机，通过 Gondolin extension 把 built-in tools 和 ! 命令路由到 micro-VM。 这三种方案隔离的对象不同，尤其第三种只会自动接管被覆盖的工具，其他 Extension Tool 仍可能在宿主机运行。 containerization 选择表 正是在提醒这个边界。

按实际运行环境确认权限。 Pi 提供拦截关口，但默认权限边界仍是操作系统用户；project trust 只管理项目资源是否加载。

十一、怎样判断 Pi 是否适合你的任务

工程压力 Pi 核心接住什么 仍需你决定什么 失败边界
多 provider coding agent 统一流式消息、tool call、usage、thinking 和 error contract。 模型选择、认证来源、代理与 provider 扩展。 自定义 provider 必须维持统一 stream contract。
长时间工具任务 事件、并发工具批次、steering/follow-up、abort 与 retry 接点。 哪些工具并行、哪些副作用要审批。 默认没有逐次权限弹窗。
可恢复的探索过程 append-only JSONL tree、leaf、fork/clone、branch summary。 何时换分支，是否总结离开的路径。 summary 有损，但原始账本仍在。

团队自定义工作流 Extensions、Skills、packages、SDK/RPC 接入面。 plan、sub-agent、MCP 暴露与认证、权限及 sandbox 策略。 扩展代码与 skill 进入同一信任边界，必须审查。

Pi 把模型接入、运行循环和会话管理做成可嵌入的包，再通过扩展组织具体工作方式。它的设计取舍是让核心职责保持清楚，让应用能替换审批、规划和协作策略。这些策略进入产品后，仍需由应用验证权限、恢复和外部副作用。需要横向比较这些职责时，可以参照Agent 框架总览。
