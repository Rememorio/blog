Codex 源码阅读 · 第一篇

从一次 turn 看懂 Codex：它不是聊天壳，而是受控运行时

读 Codex 源码，最容易走偏的方式是从目录树开始。更稳的办法是拿一条普通请求， 追问它离开 UI 以后由谁接住、谁拥有上下文、谁能批准副作用、最后哪些证据会留下来。

项目：openai/codex 主题：series overview 范围：公开源码与官方文档

先想一个非常日常的请求：你让 Codex 在当前仓库修一个 bug，必要时跑测试。 如果它只是“聊天界面加模型”，实现上把这句话发给模型、把回复流回来就够了。 但真正的 coding agent 不能这么简单。它可能要读文件、改文件、跑命令、处理测试输出、遵守 AGENTS.md、等待审批、在 sandbox 里重试、把工具结果送回模型，还要让 UI 看到可靠的进度。

所以源码阅读的第一步，不是问“哪个目录最重要”，而是问： 一条用户请求进入系统后，下一步由哪个 owner 做决定？ owner 在这里不是权限头衔，而是负责某个状态和边界的运行时组件。请求每换一次 owner， 我们就换一个源码视角。

这篇总览的核心判断是：Codex 不是一个 UI 壳，也不是模型直接操控文件系统。 它更像一个 受控 agent runtime：入口只接收意图，protocol 负责类型化， session/turn 拥有运行状态，tool gate 才能把模型请求变成副作用，event/rollout 留下可展示和可恢复的证据。

证据边界。 本文把官方文档当作产品层契约，把 openai/codex 的公开源码当作机制证据。 源码链接固定到同一个公开快照。像“受控运行时”“owner”“projection”这类词，是从可见类型、 函数和调用边界归纳出的工程读法，不是对 OpenAI 私有服务拓扑的断言。

这篇的阅读契约也很具体：读完以后，你应该能把一次普通 turn 复述成一条链路， 而不是一堆目录名。我们只追五个问题：

  1. 为什么入口代码不是架构本身？
  2. 用户意图离开入口后，由什么 typed carrier 承载？
  3. 哪一个对象真正拥有 turn 的上下文、取消、模型流和工具循环？
  4. 为什么模型输出不能直接等同于文件修改或命令执行？
  5. 客户端看到的进度，为什么只是运行时证据的一种 projection？

一、先跟一条请求走，而不是先逛目录

Codex 的仓库足够大，任何入口都能让人觉得自己摸到了核心。你可以从 CLI 读到命令解析， 从 TUI 读到状态渲染，从 app-server 读到多客户端协议，从 tools 读到 shell 和 patch， 从 sandbox 读到权限隔离。问题是，这些都是真的，但都不是单独的全貌。

更好的路线是从“修一个 bug”这条请求出发。每一步只问当前 owner 已经做完什么， 它把什么 typed fact 交给下一个 owner。

turn 阶段 阅读问题 先看哪里 后续文章
入口 哪个产品面接收请求，它拒绝在本地决定什么？ CLI、TUI、app-server、MCP server、remote-control。 入口与多客户端。
typed carrier 意图被包装成哪个 operation，输出又以哪个 event 返回？ Submission、Op、Event、EventMsg。 protocol 与事件流。
session / turn 谁拥有上下文、取消、pending input、模型流和工具循环？ Codex facade、Session、run_turn。 session 与 turn loop。
context / model 哪本账被保存，哪一份 view 被送进模型？ ContextManager、TurnContext、for_prompt()。 上下文管理。
tool authority 模型请求行动时，谁能审批、拒绝、sandbox、重试和记录输出？ ToolRouter、ToolOrchestrator、exec、apply_patch、hooks。 工具、权限与 sandbox。
projection / evidence UI 看到的内容和持久证据如何分开？ events、turn items、rollout、app-server 映射、TUI rendering。 客户端投影与恢复。

这张表不是目录，而是一个读源码时的换挡规则：当 owner 变了，文件就该换； 当 owner 没变，继续读当前层。这样不容易把“我最先看懂的文件”误当成系统中心。

二、入口只接收意图，protocol 才是第一道边界

Codex 暴露很多入口，这是产品事实；但源码里的第一道架构边界不是某一个入口， 而是入口把请求变成 typed operation 的那一刻。 SessionSource 已经把 Cli、VSCode、Exec、Mcp、SubAgent 等来源放在同一个会话来源枚举里。这个枚举的意义不是“入口很多”这么简单， 而是告诉我们：入口是来源标签，后面还要进入共享 runtime。

2.1 Submission / Op 把意图变成 typed data

在 protocol 层， Submission 不是一段聊天文本。它有 id、op、可选的客户端消息 id 和 trace。 Op 也不是单一的 prompt 字段：它可以表示用户输入、thread settings、approval、interrupt、realtime conversation、 tool refresh 等不同操作。

这就把用户请求从 UI 句子提升成了 runtime work item。比如“修 bug”可能同时带着当前 cwd、 thread settings、额外上下文、输出 schema 或审批策略。源码阅读到这里就不能再说“用户发了一句话”， 更准确的是：入口提交了一个带 id 的 typed operation。

2.2 Codex facade 是 queue pair，不是 UI 组件

typed operation 进入 core 后，会落到高层 Codex facade。这个结构持有 tx_sub、rx_event、agent status 和 session。 submit() 给 operation 生成 submission id 并送入队列； next_event() 从事件队列取回运行时输出。

这就是 Codex 的第一条不变量：客户端提交 operation，运行时返回 event。 只要抓住这个 queue pair，就不会把某个 UI 的状态管理误读成 agent runtime 的真相。

三、turn 才是 agent runtime 的控制单元

进入 session 之后，真正把上下文、模型、工具和取消揉在一起的，是 turn。 run_turn 的注释说得很朴素：每次 sampling request 里，模型要么返回 function calls，要么返回 assistant message； 如果是 function call，runtime 执行工具并把 output 放进下一次 sampling；如果只是 assistant message， 就记录历史并认为 turn 完成。

这段代码的关键不是“它循环调用模型”，而是循环前后的 owner 边界。turn 开始先跑 pre-sampling compact， 再记录上下文更新、构建 skills/plugins 注入项、跑 session start hooks、记录输入、设置上一轮配置， 进入循环后才从 history 投影出 for_prompt() 的模型输入。 

one user turn, shape-level:
  submit typed Op
  -> session accepts Submission
  -> run_turn owns this request
  -> update context / skills / hooks
  -> project history into model input
  -> stream model response
  -> execute requested tools through authority gates
  -> emit events and durable evidence

turn 的上下文也不是一条消息。 TurnContext 持有模型、cwd、权限、approval policy、sandbox、技能上下文、输出 schema、环境信息、网络策略和 session source。 它像本轮运行的结构化快照。第二篇会专门讲它怎样进入 context ledger，这里只先记住一点： turn 是运行单元，不是聊天轮次的别名。

四、模型输出只是请求，tool gate 才能给权限

现在看最容易误读的一步：模型让 Codex “执行命令”或“修改文件”。 严格说，模型并没有直接获得执行权。它只能在 model-visible tool specs 允许的范围内提出 tool call。 build_prompt() 把投影后的 input、router.model_visible_specs()、parallel tool call 能力、base instructions、 personality 和 output schema 合成 Prompt。工具 schema 在这里是模型可见能力，不是执行结果。

这份 schema 来自 built_tools() 和 ToolRouter： MCP tools、plugins、apps、dynamic tools 和 extension executors 会被合并成一套 turn-scoped router。 当模型真的返回 tool call 时， router dispatch 才把调用交给注册的工具执行器。

更关键的是执行前还有 authority 层。 ToolOrchestrator 文件头 直接把顺序写出来：approval、select sandbox、attempt、sandbox denial 后升级重试。 在具体实现里， orchestrator 会先根据 approval policy、filesystem sandbox policy 和工具自己的 requirement 做审批判断， 再选择初始 sandbox，并把 workspace roots、网络策略和平台 sandbox 参数一起带到 attempt。

所以“模型改了文件”只是用户视角的简写。源码视角应该说： 模型提出 tool call，runtime 经过 router、approval、hooks、sandbox 和具体 handler 才可能产生副作用。

五、客户端看到的是 projection，不是唯一事实源

runtime 运行时会不断发事件。 Event 和 EventMsg 把输出也类型化：warning、context compacted、thread rolled back、turn started、turn complete、 agent message delta、tool call、token count、hook lifecycle 等都不是一段无结构日志。 客户端可以把它们渲染成聊天气泡、进度条、diff、审批弹窗或状态文本，但这些 UI 形态只是 projection。

还有另一种更耐久的证据： RolloutItem 会保存 session metadata、response items、compacted records、turn context 和 event messages。 这就是为什么后面讲 resume、rollback、compact 时不能只看 UI 上还显示了什么。 UI 是当前投影，rollout 才是恢复和审计时要回放的证据层之一。

六、这个系列会怎么拆

总览篇只负责建立路线。后面的文章会沿同一条 turn 链路，一次只拆一个 owner。 这样读起来不会变成“源码百科”，也不会把所有概念一次性塞满。

篇章 核心问题 主线 owner 状态
一、总览 一次用户 turn 如何穿过入口、protocol、runtime、tool gate 和 evidence？ Submission、Codex、run_turn、ToolOrchestrator。 本文。
二、上下文管理 为什么 context 不是聊天记录，而是可投影、可压缩、可恢复的 ledger？ ContextManager、TurnContext、for_prompt()、compaction。 已发布。
三、protocol 与事件流 客户端和 runtime 如何用 typed request/event 维持同一套事实？ Op、EventMsg、app-server protocol、generated schema。 计划。
四、工具系统 工具 schema 如何进入模型，tool call 又怎样被分发、并行和归档？ ToolRouter、registry、MCP、dynamic tools、extension tools。 计划。
五、权限与 sandbox 模型请求副作用时，审批、hooks、sandbox、exec policy 分别拦在哪里？ ToolOrchestrator、exec policy、hooks、sandboxing、apply_patch。 计划。
六、客户端投影 TUI、app-server 和持久记录如何展示同一套运行时证据？ event mapping、turn items、rollout、thread status。 计划。
七、扩展与多 agent skills、plugins、MCP、subagents 怎样作为 turn-scoped 注入，而不是另起一套混乱循环？ skills manager、plugins manager、MCP exposure、multi-agent session source。 计划。

七、几个常见误读

误读 更准确的读法 为什么重要
CLI 是 Codex 的架构中心。 CLI 是入口之一；进入 runtime 后靠 Submission 和 Event 交接。 否则会把参数解析误当成 session/turn 语义。
turn 就是聊天里的一问一答。 turn 是控制单元，里面可能有多次 sampling、工具调用、pending input 和 compact。 否则看不懂为什么一次用户请求里会有多个模型请求。
模型直接运行命令。 模型只提出 tool call，执行权在 router、approval、hooks、sandbox 和 handler。 否则会漏掉最关键的安全和可审计边界。
UI 看到的历史就是 runtime truth。 UI 是 event 和状态的 projection；恢复还要看 rollout、history 和 turn context。 否则 resume、rollback、compact 都会被误读成显示层行为。

八、可以带走的规则

如果以后读别的 agent 系统，也可以先拿这套问题去试：

阅读动作 先问什么 保护什么
读入口 它把意图交给哪个 typed carrier？ 不把 UI 文本误读成 runtime work。
读 runtime 谁拥有上下文、取消、状态变更和完成条件？ 找到真正的控制点，而不是停在调用模型的那一行。
读工具 模型输出到副作用之间有哪些 gate？ 把能力暴露、审批、sandbox、执行和证据分开。
读客户端 屏幕上看到的内容来自哪些 event 和持久记录？ 区分展示层、恢复层和模型可见层。
读系列文章 这一篇正在解释哪一个 owner？ 避免所有概念同时展开，保持循序渐进。

下一篇就从这条链路里的 context owner 开始。 Codex 的上下文不是简单聊天记录，而是一个能投影给模型、能被 compact 重写、能从 rollout 恢复的运行时账本。 只有先看完这张总览图，第二篇里的 ContextManager、TurnContext 和 for_prompt() 才不会变成孤立名词。
